# 🌱 規模と安定性について — なぜ Spica は「大人数」に向かないのか

> **このプロジェクトは、1 人の学生がメインで開発しているプロジェクトです。**
> **大人数でのテストは限定的で、不安定になる可能性があります。**
> まずは**少人数のコミュニティ**（友だち同士・サークル・研究室・家族など）での利用を想定しています。

Spica は「小さく始めて、自分で面倒を見られる範囲で運用する」ことを大切にして作っています。
このドキュメントは、その前提を隠さずに書くためのものです。**できること**ではなく、
**どこで詰まるか**と、**それをどう直したか**を正直にまとめました。

2026-09 に**負荷試験を実施し、そこで見つかった詰まりは直しました**（読み取りが 2 桁速くなっています）。
そのうえで、**まだ残っている制約**（[🧱 なぜ大人数に向かないのか](#-なぜ大人数に向かないのか理由)）と、
**直したもの**（[✅ 直したこと](#-直したこと2026-09)）を分けて書いています。

---

## ✅ 結論から

- **設計の性格は変わっていません。** 既定は「SQLite + 1 プロセス + 追加ミドルウェアなし」で、
  これは小規模のための設計です。CPU を増やして速くするには複数プロセスが要り、そのためには
  Redis が必要です（任意依存として実装済み・2 ノードで動作を検証済み）。
- 作者の環境で**負荷試験を実施しました**（重い利用者 1 人を同時 20 接続で叩く条件）。
  読み取りは**毎秒 500〜1,200 リクエスト、p50 は 8〜37ms、エラー 0** で返りました。
  最初の試験で見つかった詰まり（ホームタイムラインのクエリなど 4 つ）は**直してあります**。
- **それでも「数百人が同時に活発に使える」ことを保証するものではありません。** 測ったのは
  単一利用者の繰り返しで、多様なフォロー数・多様な画面が混ざる実際の分布や、長時間の連続稼働は
  検証していません。**この検証が、いま残っているいちばん大きな課題です。**
- 数千人規模は、いまの設計の延長では届きません（[🔭 これからの設計変更](#-これからの設計変更)）。
- 「使ってはいけない」という話ではありません。大人数で使う場合は、運用する人が
  「どこが先に限界になるか」を知ったうえで調整してください（[🛠 大人数で使うなら（緩和策）](#-大人数で使うなら緩和策)）。

## 🧱 なぜ大人数に向かないのか（理由）

Spica は**追加のミドルウェアを増やさず、1 つのプロセスで完結させる**設計です。
小規模ではこれが強みになります（Redis もジョブワーカーも要らず、1 コマンドで起動できます）が、
大人数では次の点が制約になります。**ここに挙げるのは、いまも残っている制約です**
（2026-09 に直したものは次の章にまとめました）。

| 制約 | Spica の作り | 大人数で起きること |
| :--- | :--- | :--- |
| **1 プロセス・1 コア（既定）** | `cluster` も worker thread も使わず、Node.js のプロセス 1 つでリクエストも連合も処理します | **CPU を増やしても速くなりません。** 実測では 1 プロセスで 517 req/s（重い利用者・同時 20）。それを超えるには複数プロセスが要ります |
| **複数プロセスは Redis が前提** | レートリミッター・SSE の接続一覧・設定キャッシュ・定期処理のロックを Redis に移しました（**任意依存**） | Redis を入れなければ 1 本のままです。入れると増やせますが、**運用対象が 1 つ増えます**（落ちても本体は動きます → [REDIS.md](REDIS.md)） |
| **既定の DB は SQLite（1 ライタ）** | `node:sqlite` の接続 1 本。書き込みは直列で、読み取りも**同期 API** です | 実測で書き込み 742 投稿/秒。読み取りは 1 コアを占有し、**遅いクエリを 1 本書き足すと全部が止まります**。**PostgreSQL に切り替えられます**（[POSTGRESQL.md](POSTGRESQL.md)）が、PostgreSQL 側も単一ノード前提でレプリケーションはありません |
| **メディアはローカルディスクが既定** | アップロードは `server/uploads` に置き、配信もアプリが担います（Cloudflare R2 / S3 も使えます） | 画像の多いタイムラインでディスク I/O と帯域を食います。**複数プロセスにするなら R2 / S3 が必須**です（別ホストとディスクを共有できません） |
| **アンテナ（通知つき）は投稿ごとに全件走査** | 投稿が 1 件できるたびに、`notify = 1` のアンテナを全部見ます（条件によってはアンテナごとにフォロー確認のクエリを 1 本） | アンテナを使う人が増えると「投稿数 × アンテナ数」で効きます。**いまはアンテナが 0 件なので無害**ですが、使い始める前に直したい箇所です |
| **検索は近似** | SQLite は FTS5、PostgreSQL は trigram。PostgreSQL では順位を `published_at` で代用しています | 件数と内容は合いますが、語の出現頻度を考えた順位（bm25 相当）にはなりません |
| **連合で DB が育つ** | 管理画面でリレーを購読すると、リモートの投稿が次々に流れ込みます（既定で 1 日 1 回の自動メンテナンスで古い投稿を整理） | ディスクとメモリを食います。**保持期間と上限を決めておく前提**です |
| **エクスポートと削除はリクエスト内** | データの ZIP 生成・アカウント削除を、その場で実行します | 待たされます。利用者に直接効くので、次にジョブキューへ載せたい処理です（土台はあります） |
| **通知はベストエフォート** | Web Push もメールも、届かなくても本体は動きます（SMTP 未設定ならメールは送られません） | 通知の取りこぼしがあり得ます |
| **多様な利用者の負荷は未検証** | 負荷試験は「1 人の重い利用者 × 同時 20 接続」 | 数百人が同時に、それぞれ違う画面を見る状況は**測っていません**。長時間の連続稼働（メモリ・WAL・ジョブの滞留）も未検証です |

2026-09-25 に**負荷試験を実施し、そこで見つかった壁を直しました**。**直す前と後で 2 桁変わっています**
（直したものの一覧は [✅ 直したこと](#-直したこと2026-09)、方法と生の数字は
[🧪 負荷試験の結果（実測）](#-負荷試験の結果実測)）。

- 読み取りは、重い利用者 1 人を同時 20 接続で叩いて **毎秒 500〜1,200 リクエスト・p50 8〜37ms・エラー 0**
  （直す前は 3.2〜24 req/s・p50 0.5〜6.5 秒）。
- 書き込みは **毎秒 742 投稿（SQLite）/ 2,597 投稿（PostgreSQL + Redis・2 プロセス）**。
- ただし**レート制限（既定で 1 IP あたり 600 回/分＝毎秒 10 回）が先に効きます。** 上の数字は
  レート制限を外して測った「アプリ本体の力」です。

**それでも「何人まで大丈夫か」を保証はできません。** 測ったのは 1 人の重い利用者の繰り返しなので、
次の表は「どこまで検証済みか」として読んでください。

| 規模 | 見通し |
| :--- | :--- |
| 〜数十人（同時に数人） | 想定内。作者の環境で確認している範囲です |
| 同時 20 人（重い利用者） | **実測済み。ホームが 55% 混ざっても p50 37ms（SQLite）で返ります** |
| 数百人 | 射程に入りました（同時 20 で 500〜1,200 req/s なので、1 人あたり毎秒 1 回未満の利用なら余裕があります）。ただし**測ったのは「1 人の重い利用者を 20 並列で叩く」条件**で、多様な利用者が混ざる実際の分布での検証はこれからです |
| 数千人以上 | Spica の設計（1 プロセス・追加ミドルウェアなし）のままでは荷が重いです。PostgreSQL + Redis + 複数プロセスに進んでも、パーティションやレプリカはこれからの領域です |

## 🧪 負荷試験の結果（実測）

> 2026-09-25、作者の PC（Windows / 16 コア / アプリと負荷をかける側は同じマシン）で測りました。
> **絶対値ではなく構成どうしの比較**として読んでください。道具は `scripts/load-test.ts` です。

### 方法

- **データ**: ライブの SQLite をスナップショットして使いました（投稿 267,855 件・作者 7,541 人・
  ローカル投稿 24 件）。同じデータを PostgreSQL へ移送し、**両構成でまったく同じ DB** にしています
  （「直す前」の測定は 4% 少ないスナップショット。投稿 257,259 件）。
- **利用者**: 負荷試験用のアカウント 1 つが、**投稿数の多い 150 人をフォロー**（ホームの候補は約 10 万件）。
  リレーを購読しているインスタンスの「重い利用者」の想定です。
- **負荷**: 同時 20 接続。読みの内訳はホーム 55% / ローカル 15% / 連合 15% / それ以外 15%。
  SSE を 30 本つないだまま 45 秒（書き込みの試験は 30 秒）。
- レート制限は無効（`RATE_LIMIT_DISABLED=true`）、自動メンテナンスと自動バックアップも無効。
  SQLite は `ANALYZE` 済み、PostgreSQL は `VACUUM ANALYZE` 済み。Redis は 5.0（ローカル）。
- **PostgreSQL 側はチューニングしていません**（`shared_buffers` は既定の 128MB、`DATABASE_POOL_MAX` も既定の 5）。
  「素の設定でどれくらいか」を見るためです。本番向けの設定は [SETUP_PostgreSQL_Redis.md](SETUP_PostgreSQL_Redis.md) を参照してください。

（直す前の測定は 4% 少ないスナップショット。投稿 257,259 件）。

> - 「読み（連合も外す）」は、いちばん重い 2 本（ホームと連合）を除いた素の読み比べです

>   （SQLite 40 スイート / PostgreSQL 24 スイート。ページングや可視性の検査を含みます）。

### 分かったこと（と、直したこと）

#### 1. 最初の壁はホームタイムラインだった → ✅ 直しました

`api.ts` のホームの条件はこうなっていました。

```sql
WHERE (p.is_local = 1 OR p.author_url IN (SELECT following_url FROM follows WHERE follower_url = ?))
ORDER BY timeline_at DESC, p.id DESC LIMIT 21
```

SQLite も PostgreSQL も、この形だと**フォロー中の 150 人が書いた約 10 万件をいったん全部読んでから
並べ替えます**（21 件だけ欲しいのに）。1 回 0.3〜0.6 秒、SQLite では同期ドライバなので
**その間プロセス全体が止まっていました**（同時 20 の試験では、`/health` まで 3.7 秒かかりました）。

**直した形（実装済み）**: 条件を `follows` の JOIN に変えると、索引（`published_at DESC`）を逆順に
たどって 21 件見つかった時点で止まります。**同じデータ・同じ索引で 596ms → 0.1ms（SQLite）、
265ms → 0.7ms（PostgreSQL）**。スキーマ変更も `ANALYZE` も要りません。

```sql
FROM posts p
LEFT JOIN follows f ON f.following_url = p.author_url AND f.follower_url = ?
WHERE (p.is_local = 1 OR f.follower_url IS NOT NULL)
ORDER BY p.published_at DESC, p.id DESC LIMIT 21
```

`follows` は `UNIQUE(follower_url, following_url)` なので、JOIN で行が増えることはありません
（`f.id IS NOT NULL` でも同じ）。この書き換えで、同時 20 接続のホーム中心の負荷が
**3.2 → 517 req/s（p50 6.5 秒 → 37ms）**になりました。

#### 2. PostgreSQL の数字が悪かったのも「エンジン」ではなく「クエリの形」だった → ✅ 直しました

PostgreSQL 構成の読み取りが 24 req/s しか出なかったので切り分けました。**PostgreSQL が遅いのではなく、
いまのクエリの形が PostgreSQL にだけ不利でした**（SQLite の `MERGE` が偶然それを救っていました）。

同じ `UNION ALL` + 外側 `ORDER BY` + `LIMIT` でも、SQLite は `MERGE` で**流し読み**して 21 件で止まります。
PostgreSQL は枝を**全部並べ替えてから**上位 21 件を取るため、**コストが「枝の行数」に比例**します。

| 何が遅かったか | 実測（PostgreSQL） | 直した形（実測） |
| :--- | ---: | ---: |
| 連合タイムライン（枝 = 全投稿 28 万件） | 812 ms（52 万ページ） | **0.8 ms** |
| ローカルタイムライン（枝 = ローカル投稿 2.6 万件） | 226 ms | **0.3 ms** |
| ホーム（枝 = フォロー中の投稿 10 万件） | 265 ms | **0.7 ms** |
| `server-info` の投稿数（`COUNT(*) WHERE is_local = 0` を毎回） | 242 ms | **0 ms**（60 秒キャッシュ） |

どれも**枝ごとに `ORDER BY` + `LIMIT` を押し込む**（ホームは `follows` を JOIN する）と同じ直し方です。
直す前の PostgreSQL は、10 本の接続（2 プロセス × `DATABASE_POOL_MAX` 5）が全部 `active` で
1 リクエストあたり 0.2〜0.4 秒の DB 時間を食い、**プールが埋まって 24 req/s で頭打ち**でした。
クエリがサブミリ秒になったことで、この頭打ちは消えています（**24 → 1,207 req/s**）。

> 補足: ローカルタイムラインは**ローカル投稿が増えるほど遅くなります**（24 件のときは 0.5ms、
> 2.6 万件で 226ms）。小さいうちは気づかないので、育てば急に効いてくる種類の壁でした。
> 高並列時は PostgreSQL の並列クエリ（`Gather`）がワーカー待ち（`IPC`）で 1.5 秒以上滞留するのも観察しました。
> 短いクエリを大量にさばく使い方では `max_parallel_workers_per_gather = 0` も検討の余地があります
> （直す前の形では 226ms → 159ms になりました）。

#### 3. 書き込みは PostgreSQL が 3.5 倍

1 アカウントからの連投で、SQLite 742 投稿/秒・PostgreSQL + Redis（2 プロセス）2,597 投稿/秒。
SQLite は書き込みが直列なので、この差はプロセス数を増やしても広がりません（1 ファイル 1 ライタ）。
`DATABASE_POOL_MAX` は既定の 5 のまま測っています。

#### 4. 高レートで投稿すると ID が衝突していた → ✅ 直しました

直す前は、毎秒数百投稿の連投で `UNIQUE constraint failed: posts.id` により**投稿の 0.5〜1.5% が 400 で
失敗**していました（733 投稿/秒で 1.5%）。`posts.id` が `${actorUrl}/posts/${Date.now()}`（ミリ秒）
だったため、同じミリ秒に 2 件入ると主キーがぶつかっていました。

**直し方**: 通知（`notif_...`）やメディア（`media_...`）と同じく、**ミリ秒 + ランダム 4 バイト**に揃えました
（`server/src/ids.ts` にまとめ、投稿の作成と、連合から届いた活動に `id` が無いときのフォールバック
5 か所で使っています）。時刻を残しているので、ログや保存順を見たときに前後関係は分かります。

```ts
// 直す前: `${actorUrl}/posts/${Date.now()}`
`${actorUrl}/posts/${Date.now()}_${crypto.randomBytes(4).toString('hex')}`
// 例: .../users/bench/posts/1790325592803_de961912
```

**直した後の実測**: SQLite で **741.7 投稿/秒・4xx 0 件**（直す前は同じ条件で 337 件 = 1.5%）、
PostgreSQL + Redis（2 プロセス）で **2,596.7 投稿/秒・4xx 0 件**。

#### 5. SQLite の「重いクエリが全部を止める」問題は、重いクエリが無くなって解消

直す前は、ホーム 55% の負荷で `/health` が 3.7 秒かかっていました。CPU 不足ではなく
（CPU は 16 コア中 1.1 コア分）、`node:sqlite` が同期 API なので**重いクエリの間イベントループが
止まる**ためです。クエリがサブミリ秒になった今は、ホーム 55% の混在でも全エンドポイントが
p50 40ms 以下で返っています（同期ドライバという性質自体は残っているので、
**遅いクエリを足すとまた同じことが起きます**）。

### 再現するには

```bash
# 1. スナップショットを取って、負荷試験用の利用者を仕込む
node -e "new (require('node:sqlite').DatabaseSync)('server/data_astrabit.sqlite',{readOnly:true}).exec(\"VACUUM INTO '.bench/bench.sqlite'\")"
npx tsx scripts/load-test-seed.ts --db .bench/bench.sqlite --follows 150 --token-out .bench/token

# 2. ノードを起動（例: SQLite / 3900 番）
PORT=3900 DB_PATH=.bench/bench.sqlite DOMAIN=localhost:3900 \
  RATE_LIMIT_DISABLED=true AUTO_MAINTENANCE=false npx tsx server/src/index.ts

# 3. 負荷をかける
npx tsx scripts/load-test.ts --url http://localhost:3900 --token "$(cat .bench/token)" \
  --duration 45 --concurrency 20 --home-share 0.55 --sse 30
```

> [!NOTE]
> ライブの DB では実行しないでください。負荷試験は投稿を作ります（`--write 0` なら読みだけです）。

## 🛠 大人数で使うなら（緩和策）

効きやすい順に並べています。**1 番目は「買い物」ではなく「測る」です** — どこが先に詰まるかは
環境で変わります（リレーを購読していなければ DB ではなくメモリかもしれません）。

1. **まず自分の環境で測る** — `scripts/load-test.ts` がそのまま使えます。手順は
   [🧪 負荷試験の結果（実測）](#-負荷試験の結果実測) の「再現するには」。**測らずに DB を替えても、
   ボトルネックが別の場所なら速くなりません。**
2. **リレーの購読を見直す** — 一番効きます。必要のないリレーを外すだけで、流れ込む投稿・ディスク・
   メモリ・連合処理がまとめて減ります。
3. **DB を PostgreSQL に、プロセスを複数に（必要になったら）** — `DB_DRIVER=postgres` + `REDIS_URL` の
   2 つで、同じコードのまま複数プロセス + ロードバランサで動かせます。手順は
   [SETUP_PostgreSQL_Redis.md](SETUP_PostgreSQL_Redis.md)、設計と制約は
   [POSTGRESQL.md](POSTGRESQL.md) / [REDIS.md](REDIS.md)。
   **注意: Redis を入れずに 2 つ目のプロセスを立てると壊れます**（レート制限が別々に数えられ、
   リアルタイム更新が片側にしか届きません）。逆に、いまの SQLite + 1 プロセスでも
   実測で 517 req/s は出るので、**まず測ってから決める**のがおすすめです。
4. **メディアを Cloudflare R2 / S3 へ** — 手順は [SETUP_Normal.md](SETUP_Normal.md) にあります。
   **複数プロセスにする場合は必須**です（別のホストとローカルディスクは共有できません）。
5. **静的ファイルの配信をリバースプロキシに任せる** — Nginx の設定例（gzip と SSE の設定込み）も
   [SETUP_Normal.md](SETUP_Normal.md) にあります。
6. **メンテナンスの設定を見直す** — 既定では 1 日 1 回、自動メンテナンス（古いリモート投稿の整理・
   孤立メディアの削除・バックアップ）が走ります。保持期間とリモート投稿の上限を決めておいてください。
   SQLite なら `npm run db:maintenance` で手動実行・ドライランができます（この CLI は PostgreSQL では
   使えません。[POSTGRESQL.md](POSTGRESQL.md)）。
7. **メモリを増やす** — タイムラインの整形も連合の処理もメモリを使います。常時つながる SSE は
   1 接続あたりの消費は小さくても、数千本になると効いてきます。

## 🔭 これからの設計変更

> **ここから先はまだ実装していない話です。** 順番も含めて**案**として読んでください。

### ✅ すでに実装した土台（この章に案として書いていたもの）

`REDIS_URL` を設定したときだけ有効です（未設定なら今までどおり 1 プロセスで動きます）。
**2 ノードでの動作は [検査で確認済み](REDIS.md)です。**

- **レートリミッターの共有** — カウンタを Redis に移しました（スライディングウィンドウを Lua 1 往復で判定）。
  Redis が落ちているときはインメモリにフォールバックします。
- **リアルタイム更新（SSE）の Pub/Sub 化** — イベントを Pub/Sub に流し、全プロセスが自分の接続者へ配ります。
- **新着投稿の宛先を絞る** — 以前は接続している全員に全部を配っていました。いまは必要な人にだけ配ります
  （クライアントが `/api/streaming?streams=local,home,tag:foo` と申告します。申告の無い古いクライアントは
  今までどおり全部を受け取ります）。
- **設定とインスタンス鍵** — 変更時に通知を流し、各プロセスが読み直します。
- **定期処理の単一実行** — 予約投稿・配送再送・自動メンテナンスは、ロックを取った 1 プロセスだけが実行します
  （二重公開・二重送信を防ぐため）。
- **配送の並列化とジョブキュー** — 1 件ずつ「自分が送る」と宣言してから送るので二重送信になりません
  （`DELIVERY_CONCURRENCY`、既定 5）。汎用の `jobs` テーブルにはリンクプレビューの取得が載っています
  （`FOR UPDATE SKIP LOCKED` は使っていません — PostgreSQL 専用で SQLite では動かないためです）。

### 1. 多様な利用者での検証と、長時間の連続稼働（**いまのいちばんの課題**）

負荷試験の数字は「1 人の重い利用者を同時 20 接続で叩く」条件のものです。次に確かめたいのは:

- **多様な利用者が混ざった負荷** — フォロー数が違う複数のアカウント、複数の画面（ホーム・ローカル・
  連合・通知・検索）、ゲストの閲覧を同時に流します。1 利用者の繰り返しでは、キャッシュの効き方や
  クエリの偏りが見えません（`scripts/load-test.ts` を複数トークンに広げれば測れます）。
- **長時間の連続稼働** — メモリの増え方、SQLite の WAL の膨らみ、`jobs` / `outbox_deliveries` の滞留、
  自動メンテナンスが走ったときの影響。数時間〜数日動かして見る必要があります。
- **連合の burst** — リレーから投稿がまとめて流れてきたときに、Web の応答がどうなるか。

### 2. DB を育てる

いまの読み取りは 1 プロセスあたり 500〜1,200 req/s 出るので、ここから先は**その先の話**です。

- ✅ **索引の見直し（2026-09 に実測して追加）** — `posts(author_url, published_at DESC)` と
  `posts(is_local, published_at DESC)`。ライブデータのコピー（SQLite 20 万行 / PostgreSQL 17.8 万行）で測った結果:

  | クエリ | 索引なし | 索引あり |
  | :--- | :--- | :--- |
  | ローカルタイムライン | 155ms（SQLite）/ 44ms（PostgreSQL） | **0.1ms / 0.09ms** |
  | プロフィール（1 人分の投稿） | 147ms / 36ms | **0.0ms / 0.08ms** |
  | ホームタイムライン | 138ms / 38ms | 27ms / **34ms（PostgreSQL では効かない）** |

  - 教訓: 索引は「効くはず」で貼らず、`EXPLAIN` と実測で確かめること。ホームは予想に反して効きませんでした。
  - **ホームが遅かった本当の理由は索引ではなく、クエリの形でした**（`IN (SELECT ...)` を JOIN に変えて
    596ms → 0.1ms）。負荷試験の結果は [🧪 負荷試験の結果（実測）](#-負荷試験の結果実測) にあります。
  - 既に大きい DB では、起動時に作られる前に `CREATE INDEX CONCURRENTLY` を手で流してください
    （[POSTGRESQL.md](POSTGRESQL.md) の制約表）。

- **読み取りレプリカ** — タイムライン・検索・プロフィール表示は読み取り中心です。読み取り専用の接続先を用意して
  振り分けます（`withSession()` を使わない読み取りだけを向ける）。書き込みはプライマリのままです。
  **いまの読み取りは 1 プロセスあたり 500〜1,200 req/s 出るので、必要になるのはその先です。**
- **パーティション** — `posts` / `notifications` / `outbox_deliveries` を日付でパーティション化すると、
  保持期間の削除が `DELETE` ではなく `DROP PARTITION` になり、**大量削除で DB が詰まらなくなります**
  （いまは 1 日 1 回の自動メンテナンスが 1 件ずつ消しています）。
- **コネクションプール** — `DATABASE_POOL_MAX` を上げます（既定 5）。プロセスを増やすなら PgBouncer を前段に置きます。
- **遅いクエリの可視化** — `pg_stat_statements` を有効にして、タイムライン整形のクエリから見直します
  （読み取りの内訳は `npm run db:pg:stats` でも見られます）。
- **全文検索** — PostgreSQL 側は trigram + `published_at` の近似です。**PGroonga / pg_bigm を入れれば、
  日本語の順位付けが本物になります**（PostgreSQL の中で完結するのが利点）。Meilisearch や OpenSearch を
  別に立てる手もありますが、追加ミドルウェアが増えます。

### 3. メディアを CDN 前提にする

- すべて R2 / S3 に置き、**署名付き URL で直接配信**します（いまはアプリがプロキシして返しています）。
- 画像変換はアップロード時に 1 回だけ行います。いまの画像プロキシはローカルディスクにキャッシュするので
  無駄な再変換は避けられますが、**そのキャッシュはプロセスと同じマシンにしか効きません**。
- 前段に Cloudflare などの CDN を置けば、画像と静的なファイルの帯域をアプリから外せます。

### 4. 重い処理をリクエストから追い出す

- **タイムラインの整形**（`enrichAndFilterPosts`）は 1 リクエストで何本ものクエリを撃ちます。
  実測ではローカルタイムライン 1 回で **9 本**（`pg_stat_database` のトランザクション数で計測）、
  `server-info` は 21 本でした（こちらは 60 秒キャッシュにして解消）。クエリの本数を減らすか、
  プロセス内キャッシュ + 短い TTL（`TIMELINE_CACHE_TTL_SEC`）で「同じタイムラインを何度も組み立てない」
  ようにします。**クエリの形を直した今は、ここが次の読み取りの伸びしろ**です。
- **fan-out on write**（投稿時にフォロワーの分を書き込む方式）は読み取りが劇的に軽くなりますが、書き込みが重くなります。
  数千人規模なら、読み取り側のキャッシュを先にやるほうが現実的だと思います。
- **画像処理（sharp）をワーカーへ** — CPU とスレッドプールを Web プロセスと奪い合わなくなります。
- **Inbox の受信処理**も、重い部分をキューに積んで非同期化します。
- **アンテナ（通知つき）の判定をまとめて引く** — いまは投稿 1 件ごとにアンテナを全件見て、
  条件によってはアンテナごとにクエリを撃ちます。**1 本のクエリで「その投稿がどのアンテナに当たるか」を
  引く形**にすれば、アンテナを使う人が増えても効きません（いまは 0 件なので、使う前に直したい箇所です）。

### 5. 見えるようにする（計測と負荷試験）

- ✅ **`/health` の詳細** — DB の生存と遅延に加えて、Redis の状態・SSE の接続数・タイムラインキャッシュの
  ヒット数・配送キューの滞留・ジョブの件数が見えます（要認証）。
- ✅ **`npm run db:pg:stats`** — PostgreSQL の遅いクエリ・テーブルと索引のサイズ・未使用の索引。
- ✅ **負荷試験の道具（`scripts/load-test.ts`）** — 同時接続数・時間・読み書きの比率・SSE の本数を
  指定して回せます（結果は [🧪 負荷試験の結果（実測）](#-負荷試験の結果実測)）。
- **時系列のメトリクス（`/metrics`）はまだありません** — いま見えるのは「その瞬間」だけです。
  リクエスト数・レイテンシ・滞留数の推移を Prometheus 形式などで出せるようにすると、
  **「なんとなく重い」ではなく「いつから詰まり始めたか」で直せる**ようになります。

### どこから手を付けるか（順番の目安）

**済んだものは前の章（[✅ 直したこと](#-直したこと2026-09)）にまとめました。** ここはこれからやる分です。

| 順番 | 変更 | 解けること | 規模 |
| :--- | :--- | :--- | :--- |
| 1 | **多様な利用者が混ざった負荷で測る**（複数トークン・ばらけたフォロー数・複数の画面・長時間の連続稼働） | 「1 人の重い利用者」しか測っていない | 中（道具は `scripts/load-test.ts`） |
| 2 | **アンテナ（通知つき）の判定を 1 本のクエリに** | 投稿数 × アンテナ数（いまは 0 件なので無害） | 小 |
| 3 | エクスポート・アカウント削除を非同期ジョブへ | 利用者に直接効く待ち時間 | 中（土台はできている） |
| 4 | タイムライン整形のクエリを減らす／キャッシュする | 読み取り 1 回あたり 9 本のクエリ | 中 |
| 5 | メディアの R2 / S3 + 署名付き URL + CDN | 帯域とディスク I/O | 中 |
| 6 | `pg_stat_statements` と `/metrics`（時系列） | 常時見張る・遅いクエリを特定する | 小〜中 |

| 9 | PostgreSQL + 読み取りレプリカ | DB の読み取り負荷 | 大 |
| 10 | パーティション（`posts` / `notifications` / `outbox_deliveries`） | 保持期間の削除が重い | 大 |

> **1 番目を先頭に置いているのは、次の一手がデータで決まるからです。** いまの数字は
> 「1 人の重い利用者を 20 並列で叩く」条件なので、多様な利用者が混ざると別の場所が先に詰まる
> 可能性があります（リレーを購読していなければ DB ではなくメモリかもしれません）。

> [!NOTE]
> 上の表を進めていくと、**「1 プロセス・追加ミドルウェアなし」ではなくなります。**
