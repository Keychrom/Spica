# 🌱 規模と安定性について — なぜ Spica は「大人数」に向かないのか

> **このプロジェクトは、1 人の学生がメインで開発しているプロジェクトです。**
> **大人数でのテストができておらず、不安定になる可能性があります。**
> まずは**少人数のコミュニティ**（友だち同士・サークル・研究室・家族など）での利用を想定しています。

Spica は「小さく始めて、自分で面倒を見られる範囲で運用する」ことを大切にして作っています。
このドキュメントは、その前提を隠さずに書くためのものです。**できること**ではなく、
**どこで詰まるか**と、**それをどう直すか**を正直にまとめました。

---

## ✅ 結論から

- 作者の環境で**負荷試験を実施しました**（重い利用者 1 人を同時 20 接続で叩く条件）。
  読みは**毎秒 500〜1,200 リクエスト、p50 は 8〜37ms、エラー 0** で返りました（下の「🧪 負荷試験の結果（実測）」）。
  最初の試験で見つかった詰まり（ホームタイムラインのクエリ）は**直してあります**。
- ただし測ったのは**単一利用者の繰り返し**です。多様なフォロー数・多様な画面が混ざる実際の分布や、
  長時間の連続稼働は検証していません。**数百人が同時に活発に使う状況を保証するものではありません。**
- 「使ってはいけない」という話ではありません。大人数で使う場合は、運用する人が
  「どこが先に限界になるか」を知ったうえで調整してください（後半の「大人数で使うなら（緩和策）」を参照）。

## 🧱 なぜ大人数に向かないのか（理由）

Spica は**追加のミドルウェアを増やさず、1 つのプロセスで完結させる**設計です。
小規模ではこれが強みになります（Redis もジョブワーカーも要らず、1 コマンドで起動できます）が、
大人数では次の点が制約になります。

| 制約 | Spica の作り | 大人数で起きること |
| :--- | :--- | :--- |
| **単一プロセス** | `cluster` も worker thread も使わず、Node.js のプロセス 1 つでリクエストも連合も処理します | CPU を増やしても速くなりません。画像処理・連合配送・タイムライン整形が重なると、他のリクエストの待ち時間が伸びます |
| **複数プロセスに分けられない** | レートリミッターはインメモリ、リアルタイム更新（SSE）の接続一覧もプロセス内、設定とインスタンス鍵は起動時にメモリへ読み込みます | 2 つ目のプロセスを立てると、レート制限が別々に数えられ、リアルタイム更新が片方の利用者にしか届かず、設定変更も片方にしか反映されません（**`REDIS_URL` を設定すると解消します** → [REDIS.md](REDIS.md)） |
| **配送と背景処理** | 連合配送の再送（`outbox_deliveries`）と汎用のジョブキュー（`jobs`）を、アプリ内のワーカーが回しています | プロセスが落ちている間は止まります（復帰後に再開）。**配送は 1 件ずつ「自分が送る」と宣言してから送るので、複数プロセスでも 1 プロセス内でも並列に送れます**（`DELIVERY_CONCURRENCY`） |
| **既定の DB は SQLite** | `node:sqlite` の接続 1 本。書き込みは直列です | 書き込みが混み合うと待ちます。**PostgreSQL に切り替えられます**（[POSTGRESQL.md](POSTGRESQL.md)）が、PostgreSQL 側も単一ノード前提で、レプリケーションやシャーディングはありません |
| **メディアはローカルディスクが既定** | アップロードは `server/uploads` に置き、配信もアプリが担います（Cloudflare R2 / S3 も使えます） | 画像の多いタイムラインでディスク I/O と帯域を食います |
| **検索は近似** | SQLite は FTS5、PostgreSQL は trigram。PostgreSQL では順位を `published_at` で代用しています | 件数と内容は合いますが、語の出現頻度を考えた順位（bm25 相当）にはなりません |
| **連合で DB が育つ** | 管理画面でリレーを購読すると、リモートの投稿が次々に流れ込みます | ディスクとメモリを食います。既定では 1 日 1 回の自動メンテナンス（古いリモート投稿の整理・バックアップ）が走りますが、保持期間と上限を決めておく前提です |
| **通知はベストエフォート** | Web Push もメールも、届かなくても本体は動きます（SMTP 未設定ならメールは送られません） | 通知の取りこぼしがあり得ます |

## 📈 どのくらいから厳しくなるのか

2026-09-25 に**負荷試験を実施し、そこで見つかった壁を直しました**（方法と数字は下の
「🧪 負荷試験の結果（実測）」）。**直す前と後で 2 桁変わっています。**

| 同時 20 接続での実測 | 直す前 | 直した後 |
| :--- | ---: | ---: |
| SQLite 既定・読み（ホーム 55%） | 3.2 req/s（p50 6.5 秒） | **517 req/s（p50 37ms）** |
| PostgreSQL + Redis（2 プロセス）・同じ | 6.6 req/s（p50 2.8 秒） | **647 req/s（p50 29ms）** |
| SQLite 既定・投稿のみ | 467 投稿/秒 | **742 投稿/秒**（4xx も 0 に） |
| PostgreSQL + Redis・投稿のみ | 2,046 投稿/秒 | **2,805 投稿/秒** |

- **いちばん効いたのはホームタイムラインの 1 クエリの書き換えでした**（`follows` を JOIN する形）。
  1 回 0.3〜0.6 秒 → サブミリ秒になり、プロセスを止めていた詰まりが消えました。
- **PostgreSQL が振るわなかったのも同じ種類の問題でした。** タイムライン系のクエリの形が
  PostgreSQL にだけ不利で（SQLite は自動で流し読みします）、1 本あたり 0.2〜0.8 秒かかっていました。
  枝ごとに `ORDER BY` + `LIMIT` を押し込むと同じくサブミリ秒になります。
- **書き込みで失敗していた ID の衝突も直しました**（毎秒 700 投稿でも 4xx は 0 件になりました）。
- ただし**レート制限（既定で 1 IP あたり 600 回/分＝毎秒 10 回）が先に効きます。** 上の数字は
  レート制限を外して測った「アプリ本体の力」です。

| 規模 | 見通し |
| :--- | :--- |
| 〜数十人（同時に数人） | 想定内。作者の環境で確認している範囲です |
| 同時 20 人（重い利用者） | **実測済み。ホームが 55% 混ざっても p50 37ms（SQLite）で返ります** |
| 数百人 | 射程に入りました（同時 20 で 500〜1,200 req/s なので、1 人あたり毎秒 1 回未満の利用なら余裕があります）。ただし**測ったのは「1 人の重い利用者を 20 並列で叩く」条件**で、多様な利用者が混ざる実際の分布での検証はこれからです |
| 数千人以上 | Spica の設計（1 プロセス・追加ミドルウェアなし）のままでは荷が重いです。PostgreSQL + Redis + 複数プロセスに進んでも、パーティションやレプリカはこれからの領域です |

## 🧪 負荷試験の結果（実測）

> 2026-09-25、作者の PC（Windows / 16 コア / アプリと負荷をかける側は同じマシン）で測りました。
> **絶対値ではなく構成どうしの比較**として読んでください。道具は `scripts/load-test.ts` です。

### 方法

- **データ**: ライブの SQLite をスナップショットして使いました（投稿 267,855 件・作者 7,541 人・
  ローカル投稿 24 件）。同じデータを PostgreSQL へ移送し、**両構成でまったく同じ DB** にしています
  （「直す前」の測定は 4% 少ないスナップショット。投稿 257,259 件）。
- **利用者**: 負荷試験用のアカウント 1 つが、**投稿数の多い 150 人をフォロー**（ホームの候補は約 10 万件）。
  リレーを購読しているインスタンスの「重い利用者」の想定です。
- **負荷**: 同時 20 接続。読みの内訳はホーム 55% / ローカル 15% / 連合 15% / それ以外 15%。
  SSE を 30 本つないだまま 45 秒（書き込みの試験は 30 秒）。
- レート制限は無効（`RATE_LIMIT_DISABLED=true`）、自動メンテナンスと自動バックアップも無効。
  SQLite は `ANALYZE` 済み、PostgreSQL は `VACUUM ANALYZE` 済み。Redis は 5.0（ローカル）。
- **PostgreSQL 側はチューニングしていません**（`shared_buffers` は既定の 128MB、`DATABASE_POOL_MAX` も既定の 5）。
  「素の設定でどれくらいか」を見るためです。本番向けの設定は [SETUP_PostgreSQL_Redis.md](SETUP_PostgreSQL_Redis.md) を参照してください。

### 結果（直す前 → 直した後）

同じ手順で、修正の前後を測りました。データはライブのスナップショット（投稿 267,855 件・作者 7,541 人・
ローカル投稿 24 件）を PostgreSQL へ移送したもので、**両構成でまったく同じ DB** です
（直す前の測定は 4% 少ないスナップショット。投稿 257,259 件）。

| 構成 | シナリオ | 直す前 | 直した後 | p50（前 → 後） |
| :--- | :--- | ---: | ---: | :--- |
| SQLite 既定（1 プロセス） | 読み（ホーム 55%） | 3.2 req/s | **517 req/s** | 6.5 秒 → 37 ms |
| SQLite 既定 | 読み（ホームなし） | 260 req/s | **670 req/s** | 69 ms → 30 ms |
| SQLite 既定 | 読み（連合も外す） | 180 req/s | **895 req/s** | 108 ms → 21 ms |
| SQLite 既定 | 投稿 30% 混在（ホームなし） | 315 req/s | **752 req/s** | 56 ms → 25 ms |
| SQLite 既定 | 投稿のみ | 467 投稿/秒 | **742 投稿/秒** | 28 ms → 22 ms |
| PostgreSQL + Redis（2 プロセス） | 読み（ホーム 55%） | 6.6 req/s | **647 req/s** | 2.8 秒 → 29 ms |
| PostgreSQL + Redis | 読み（ホームなし） | 7.9 req/s | **906 req/s** | 2.1 秒 → 20 ms |
| PostgreSQL + Redis | 読み（連合も外す） | 24 req/s | **1,207 req/s** | 559 ms → 8 ms |
| PostgreSQL + Redis | 投稿 30% 混在（ホームなし） | — | 1,269 req/s | — → 12 ms |
| PostgreSQL + Redis | 投稿のみ | 2,046 投稿/秒 | **2,597 投稿/秒** | 8.4 ms → 7.2 ms |

> - **SQLite は 1 プロセス、PostgreSQL は 2 プロセス**です。読みの差（517 対 647）はほぼプロセス数の差で、
>   PostgreSQL の強みは**プロセスを増やせること**にあります（書き込みは 3.5 倍）。
> - 「読み（連合も外す）」は、いちばん重い 2 本（ホームと連合）を除いた素の読み比べです
>   （ローカル 50% / server-info 33% / health 17%）。
> - **4xx / 5xx は 1 件も出ていません。** 直す前は投稿の 0.5〜1.5% が ID の衝突で 400 になっていたので、
>   それも直しました（後述）。
> - 書き込みの数値は実行ごとに ±10% 程度ばらつきます（読みの差はそれを超えています）。
> - ここに書いた修正は**テストを全部通したうえで入れています**
>   （SQLite 40 スイート / PostgreSQL 24 スイート。ページングや可視性の検査を含みます）。

直す前に「どこが詰まっていたか」の内訳（DB に直接クエリを投げた時間・温まっている状態・1 本ずつ）:

| クエリ | SQLite | PostgreSQL | 直した形（PostgreSQL） |
| :--- | ---: | ---: | ---: |
| ホーム | 596 ms | 265 ms | **0.7 ms**（`follows` を JOIN） |
| 連合 | 0 ms | 812 ms | **0.8 ms**（枝ごとに `ORDER BY` + `LIMIT`） |
| ローカル（ローカル投稿 2.6 万件） | 0 ms | 226 ms | **0.3 ms**（同上） |
| server-info の投稿数（`COUNT(*) WHERE is_local = 0`） | 12 ms | 242 ms | **0 ms**（60 秒キャッシュ） |

### 分かったこと（と、直したこと）

#### 1. 最初の壁はホームタイムラインだった → ✅ 直しました

`api.ts` のホームの条件はこうなっていました。

```sql
WHERE (p.is_local = 1 OR p.author_url IN (SELECT following_url FROM follows WHERE follower_url = ?))
ORDER BY timeline_at DESC, p.id DESC LIMIT 21
```

SQLite も PostgreSQL も、この形だと**フォロー中の 150 人が書いた約 10 万件をいったん全部読んでから
並べ替えます**（21 件だけ欲しいのに）。1 回 0.3〜0.6 秒、SQLite では同期ドライバなので
**その間プロセス全体が止まっていました**（同時 20 の試験では、`/health` まで 3.7 秒かかりました）。

**直した形（実装済み）**: 条件を `follows` の JOIN に変えると、索引（`published_at DESC`）を逆順に
たどって 21 件見つかった時点で止まります。**同じデータ・同じ索引で 596ms → 0.1ms（SQLite）、
265ms → 0.7ms（PostgreSQL）**。スキーマ変更も `ANALYZE` も要りません。

```sql
FROM posts p
LEFT JOIN follows f ON f.following_url = p.author_url AND f.follower_url = ?
WHERE (p.is_local = 1 OR f.follower_url IS NOT NULL)
ORDER BY p.published_at DESC, p.id DESC LIMIT 21
```

`follows` は `UNIQUE(follower_url, following_url)` なので、JOIN で行が増えることはありません
（`f.id IS NOT NULL` でも同じ）。この書き換えで、同時 20 接続のホーム中心の負荷が
**3.2 → 517 req/s（p50 6.5 秒 → 37ms）**になりました。

#### 2. PostgreSQL の数字が悪かったのも「エンジン」ではなく「クエリの形」だった → ✅ 直しました

PostgreSQL 構成の読み取りが 24 req/s しか出なかったので切り分けました。**PostgreSQL が遅いのではなく、
いまのクエリの形が PostgreSQL にだけ不利でした**（SQLite の `MERGE` が偶然それを救っていました）。

同じ `UNION ALL` + 外側 `ORDER BY` + `LIMIT` でも、SQLite は `MERGE` で**流し読み**して 21 件で止まります。
PostgreSQL は枝を**全部並べ替えてから**上位 21 件を取るため、**コストが「枝の行数」に比例**します。

| 何が遅かったか | 実測（PostgreSQL） | 直した形（実測） |
| :--- | ---: | ---: |
| 連合タイムライン（枝 = 全投稿 28 万件） | 812 ms（52 万ページ） | **0.8 ms** |
| ローカルタイムライン（枝 = ローカル投稿 2.6 万件） | 226 ms | **0.3 ms** |
| ホーム（枝 = フォロー中の投稿 10 万件） | 265 ms | **0.7 ms** |
| `server-info` の投稿数（`COUNT(*) WHERE is_local = 0` を毎回） | 242 ms | **0 ms**（60 秒キャッシュ） |

どれも**枝ごとに `ORDER BY` + `LIMIT` を押し込む**（ホームは `follows` を JOIN する）と同じ直し方です。
直す前の PostgreSQL は、10 本の接続（2 プロセス × `DATABASE_POOL_MAX` 5）が全部 `active` で
1 リクエストあたり 0.2〜0.4 秒の DB 時間を食い、**プールが埋まって 24 req/s で頭打ち**でした。
クエリがサブミリ秒になったことで、この頭打ちは消えています（**24 → 1,207 req/s**）。

> 補足: ローカルタイムラインは**ローカル投稿が増えるほど遅くなります**（24 件のときは 0.5ms、
> 2.6 万件で 226ms）。小さいうちは気づかないので、育てば急に効いてくる種類の壁でした。
> 高並列時は PostgreSQL の並列クエリ（`Gather`）がワーカー待ち（`IPC`）で 1.5 秒以上滞留するのも観察しました。
> 短いクエリを大量にさばく使い方では `max_parallel_workers_per_gather = 0` も検討の余地があります
> （直す前の形では 226ms → 159ms になりました）。

#### 3. 書き込みは PostgreSQL が 3.5 倍

1 アカウントからの連投で、SQLite 742 投稿/秒・PostgreSQL + Redis（2 プロセス）2,597 投稿/秒。
SQLite は書き込みが直列なので、この差はプロセス数を増やしても広がりません（1 ファイル 1 ライタ）。
`DATABASE_POOL_MAX` は既定の 5 のまま測っています。

#### 4. 高レートで投稿すると ID が衝突していた → ✅ 直しました

直す前は、毎秒数百投稿の連投で `UNIQUE constraint failed: posts.id` により**投稿の 0.5〜1.5% が 400 で
失敗**していました（733 投稿/秒で 1.5%）。`posts.id` が `${actorUrl}/posts/${Date.now()}`（ミリ秒）
だったため、同じミリ秒に 2 件入ると主キーがぶつかっていました。

**直し方**: 通知（`notif_...`）やメディア（`media_...`）と同じく、**ミリ秒 + ランダム 4 バイト**に揃えました
（`server/src/ids.ts` にまとめ、投稿の作成と、連合から届いた活動に `id` が無いときのフォールバック
5 か所で使っています）。時刻を残しているので、ログや保存順を見たときに前後関係は分かります。

```ts
// 直す前: `${actorUrl}/posts/${Date.now()}`
`${actorUrl}/posts/${Date.now()}_${crypto.randomBytes(4).toString('hex')}`
// 例: .../users/bench/posts/1790325592803_de961912
```

**直した後の実測**: SQLite で **741.7 投稿/秒・4xx 0 件**（直す前は同じ条件で 337 件 = 1.5%）、
PostgreSQL + Redis（2 プロセス）で **2,596.7 投稿/秒・4xx 0 件**。

#### 5. SQLite の「重いクエリが全部を止める」問題は、重いクエリが無くなって解消

直す前は、ホーム 55% の負荷で `/health` が 3.7 秒かかっていました。CPU 不足ではなく
（CPU は 16 コア中 1.1 コア分）、`node:sqlite` が同期 API なので**重いクエリの間イベントループが
止まる**ためです。クエリがサブミリ秒になった今は、ホーム 55% の混在でも全エンドポイントが
p50 40ms 以下で返っています（同期ドライバという性質自体は残っているので、
**遅いクエリを足すとまた同じことが起きます**）。

### 再現するには

```bash
# 1. スナップショットを取って、負荷試験用の利用者を仕込む
node -e "new (require('node:sqlite').DatabaseSync)('server/data_astrabit.sqlite',{readOnly:true}).exec(\"VACUUM INTO '.bench/bench.sqlite'\")"
npx tsx scripts/load-test-seed.ts --db .bench/bench.sqlite --follows 150 --token-out .bench/token

# 2. ノードを起動（例: SQLite / 3900 番）
PORT=3900 DB_PATH=.bench/bench.sqlite DOMAIN=localhost:3900 \
  RATE_LIMIT_DISABLED=true AUTO_MAINTENANCE=false npx tsx server/src/index.ts

# 3. 負荷をかける
npx tsx scripts/load-test.ts --url http://localhost:3900 --token "$(cat .bench/token)" \
  --duration 45 --concurrency 20 --home-share 0.55 --sse 30
```

> [!NOTE]
> ライブの DB では実行しないでください。負荷試験は投稿を作ります（`--write 0` なら読みだけです）。

## 🛠 大人数で使うなら（緩和策）

効きやすい順に並べています。

1. **リレーの購読を見直す** — 一番効きます。必要のないリレーを外すだけで、流れ込む投稿とディスクの増え方が大きく変わります。
2. **DB を PostgreSQL にする** — `DB_DRIVER=postgres DATABASE_URL=...`。設計・移行手順・制約は [POSTGRESQL.md](POSTGRESQL.md) にあります（既定は SQLite のままです）。
3. **メディアを Cloudflare R2 / S3 へ** — 手順は [SETUP_Normal.md](SETUP_Normal.md) にあります。
4. **静的ファイルの配信をリバースプロキシに任せる** — Nginx の設定例も [SETUP_Normal.md](SETUP_Normal.md) にあります。
5. **メンテナンスの設定を見直す** — 既定では 1 日 1 回、自動メンテナンス（古いリモート投稿の整理・孤立メディアの削除・バックアップ）が走ります。保持期間とリモート投稿の上限を決めておいてください。SQLite なら `npm run db:maintenance` で手動実行・ドライランができます（この CLI は PostgreSQL では使えません。[POSTGRESQL.md](POSTGRESQL.md)）。
6. **メモリを増やす** — タイムラインの整形も連合の処理もメモリを使います。
7. **プロセスは 1 本に保つ** — PM2 は fork モード（`pm2 start npm --name "spica" -- run start`）で使ってください。上に書いた理由で、2 つ目のプロセスを立てると壊れます。**`REDIS_URL` を設定するとこの制限は外れます**（レート制限・リアルタイム更新・設定の反映・定期処理の単一実行が共有されます → [REDIS.md](REDIS.md) / [SETUP_PostgreSQL_Redis.md](SETUP_PostgreSQL_Redis.md)）。

## 🚧 いまの Spica に無いもの

まず「無いもの」を挙げます。次章が、それをどう直すかの案です。

- 複数プロセスでの運用そのもの（**仕組みは [REDIS.md](REDIS.md) で用意しました**が、本番で回すには
  PostgreSQL と R2 / S3 が前提で、大人数での検証はこれからです）
- **多様な利用者が混ざった負荷での検証**（いまの数字は「1 人の重い利用者を 20 並列で叩く」条件です）
- 読み取りレプリカへの振り分け
- 検索の順位付け（bm25 相当）
- オブジェクトストレージ前提の最適化（いまはローカルディスクでも動く作り）
- DM（1 対 1 のメッセージ機能）は方針として実装しません。理由は README の「DM を実装しない方針」の節に書いています。

## 🔭 数千人規模でも安定させるには（設計変更と修正の案）

> **ここから先は実装済みの話ではありません。** 「こう変えれば、おそらく数千人規模でも安定するはず」という設計案です。
> ただし**第一の壁（ホームタイムラインのクエリ）とその直し方は負荷試験で裏が取れています**（上の実測）。
> それ以外は負荷をかけて確かめたうえでの数字ではないので、順番も含めて**案**として読んでください。

### 1. プロセスを何本でも立てられるようにする（水平展開）

いまアプリの状態がプロセスの中にあるので、増やせません。**状態をプロセスの外に出す**と、同じコードのまま
複数プロセス + ロードバランサで動かせるようになります。**この章の 4 つは Redis を任意依存として実装済みです**
（手順は [REDIS.md](REDIS.md)。`REDIS_URL` を設定したときだけ有効で、未設定なら今までどおりです）。

- ✅ **レートリミッター** — カウンタを Redis に移しました（スライディングウィンドウを Lua 1 往復で判定）。
  Redis が落ちているときはインメモリにフォールバックします。
- ✅ **リアルタイム更新（SSE）** — イベントを Pub/Sub に流し、全プロセスが自分の接続者へ配ります。
  （PostgreSQL の `LISTEN` / `NOTIFY` でも同じことができます。Redis を入れるならこちらのほうが素直で、
  DB の接続を 1 本専有しなくて済みます）
- ✅ **新着投稿の宛先を絞る** — 以前は接続している**全員に全部**を配っていました（クライアントが捨てていました）。
  リレーを購読していると 1 日に数万件のリモート投稿が届くので、いまは**必要な人にだけ**配ります。
  クライアントは接続時に見たいストリームを申告します（`/api/streaming?streams=local,home,tag:foo`）:
  ローカル投稿は「ローカル/ホーム」を購読している人へ、リモート投稿は「連合（all）を見ている人」と
  「作者をフォローしている人」へだけ届きます。判定材料（フォロワー一覧）は Pub/Sub のメッセージに
  含めるので、どのプロセスでも同じ判定になります（フォロワーの引き当ては 60 秒キャッシュ・
  `follows(following_url)` の索引が効きます）。申告の無い古いクライアントは今までどおり全部を受け取ります。
- ✅ **設定とインスタンス鍵のメモリキャッシュ** — 変更時に通知を流し、各プロセスが読み直します。
- ✅ **定期処理の単一実行** — 予約投稿・配送再送・自動メンテナンスは、ロックを取った 1 プロセスだけが実行します
  （二重公開・二重送信を防ぐため。速くはなりません）。
- **長期接続を別プロセスに分ける** — 数千人が常時 SSE でつなぐと、接続とソケットだけで 1 プロセスのメモリを圧迫します。
  リアルタイム配信だけを担当するプロセスに分ける（または HTTP/2 と nginx の設定を整える）ほうが安全です。
- **セッションと権限はすでに DB にあります** — この部分は変更なしで共有できます。
- **共有ファイルシステムを前提にしない** — メディアは R2 / S3 に置き、ローカルディスクはキャッシュ扱いにします。

### 2. ジョブキューをアプリの外に出す

連合配送の再送・予約投稿・メンテナンスは、アプリ内のワーカーが回しています。
**このうち配送と、汎用の背景処理は実装済みです**（2026-09）。

- ✅ **配送は並列に送れる** — 1 件ずつ「自分が送る」と宣言（条件付き UPDATE）してから送るので、
  同じ行を二重に送りません。**プロセスを増やしても、1 プロセス内でも**（`DELIVERY_CONCURRENCY`、既定 5）
  並列に送れます。`FOR UPDATE SKIP LOCKED` は使っていません — PostgreSQL 専用で、SQLite では動かないためです
  （条件付き UPDATE が取れたかどうかが判定そのものなので、どちらの DB でも同じコードで済みます）。
- ✅ **汎用のジョブキュー（`jobs` テーブル）** — バックオフつきの再試行、処理中に落ちた行の復帰、
  同じ仕事を二重に積まない `dedupeKey`、`/health` での件数表示。いまは**リンクプレビューの取得**が載っています
  （以前は 1 回投げて失敗したら諦めていました）。
- **まだリクエストの中で走っているもの**: データエクスポート（ZIP 生成）とアカウント削除。
  ここが「利用者に直接効く」次の改善です（ジョブキューに載せれば、応答を待たせずに済みます）。
- キューは PostgreSQL で足ります（専用ミドルウェアも Redis も不要）。BullMQ + Redis を選ぶ手もありますが、
  **依存を増やさないことを優先するなら DB のままでよい**と思います。

### 3. DB を育てる

- ✅ **索引の見直し（2026-09 に実測して追加）** — `posts(author_url, published_at DESC)` と
  `posts(is_local, published_at DESC)`。ライブデータのコピー（SQLite 20 万行 / PostgreSQL 17.8 万行）で測った結果:

  | クエリ | 索引なし | 索引あり |
  | :--- | :--- | :--- |
  | ローカルタイムライン | 155ms（SQLite）/ 44ms（PostgreSQL） | **0.1ms / 0.09ms** |
  | プロフィール（1 人分の投稿） | 147ms / 36ms | **0.0ms / 0.08ms** |
  | ホームタイムライン | 138ms / 38ms | 27ms / **34ms（PostgreSQL では効かない）** |

  - **PostgreSQL ではホームタイムラインに効きません。** 条件が「`is_local = 1` **または** フォロー中の
    `author_url`」の並べ替え付きなので、索引では解決せず、**次の一手は読み取りキャッシュ**（下の 8 番）です。
    SQLite では 2 本揃うと OR 最適化（MULTI-INDEX OR）が効いて 138ms → 27ms になります。
  - 教訓: 索引は「効くはず」で貼らず、`EXPLAIN` と実測で確かめること。ホームは予想に反して効きませんでした。
  - 既に大きい DB では、起動時に作られる前に `CREATE INDEX CONCURRENTLY` を手で流してください
    （[POSTGRESQL.md](POSTGRESQL.md) の制約表）。

- **読み取りレプリカ** — タイムライン・検索・プロフィール表示は読み取り中心です。読み取り専用の接続先を用意して
  振り分けます（`withSession()` を使わない読み取りだけを向ける）。書き込みはプライマリのままです。
- **パーティション** — `posts` / `notifications` / `outbox_deliveries` を日付でパーティション化すると、
  保持期間の削除が `DELETE` ではなく `DROP PARTITION` になり、**大量削除で DB が詰まらなくなります**
  （いまは 1 日 1 回の自動メンテナンスが 1 件ずつ消しています）。
- **コネクションプール** — `DATABASE_POOL_MAX` を上げます。プロセスを増やすなら PgBouncer を前段に置きます。
- **遅いクエリの可視化** — `pg_stat_statements` を有効にして、タイムライン整形のクエリから見直します。
- **全文検索** — PostgreSQL 側は trigram + `published_at` の近似です。**PGroonga / pg_bigm を入れれば、
  日本語の順位付けが本物になります**（PostgreSQL の中で完結するのが利点）。Meilisearch や OpenSearch を
  別に立てる手もありますが、追加ミドルウェアが増えます。

### 4. メディアを CDN 前提にする

- すべて R2 / S3 に置き、**署名付き URL で直接配信**します（いまはアプリがプロキシして返しています）。
- 画像変換はアップロード時に 1 回だけ行います。いまの画像プロキシはローカルディスクにキャッシュするので
  無駄な再変換は避けられますが、**そのキャッシュはプロセスと同じマシンにしか効きません**。
- 前段に Cloudflare などの CDN を置けば、画像と静的なファイルの帯域をアプリから外せます。

### 5. 重い処理をリクエストから追い出す

- **タイムラインの整形**（`enrichAndFilterPosts`）は 1 リクエストで多くのクエリを撃ちます。
  プロセス内キャッシュ + 短い TTL、またはマテリアライズドビューで「同じタイムラインを何度も組み立てない」ようにします。
- **fan-out on write**（投稿時にフォロワーの分を書き込む方式）は読み取りが劇的に軽くなりますが、書き込みが重くなります。
  **数千人規模なら、読み取り側のキャッシュを先にやるほうが現実的**だと思います。
- **画像処理（sharp）をワーカーへ** — CPU とスレッドプールを Web プロセスと奪い合わなくなります。
- **Inbox の受信処理**も、重い部分をキューに積んで非同期化します。

### 6. 見えるようにする（計測と負荷試験）

- いまは `/health` で DB の生存と遅延が見えるだけです。**時系列のメトリクス**（`/metrics`）を足します:
  リクエスト数・レイテンシ・SSE の接続数・`outbox_deliveries` の滞留数・コネクションプールの使用率。
- **滞留数と遅いクエリが見えれば、「なんとなく重い」ではなく「どこが詰まっているか」で直せます。**
  上の設計変更は、結局は測って確かめる以外に正しさを保証する方法がありません。
- ✅ **負荷試験は `scripts/load-test.ts` で回せるようになりました**（結果は上の「🧪 負荷試験の結果（実測）」）。
  k6 のような外部ツールは要らず、依存も増やしていません。自分のデータで同じ手順を再現できます。

## 👤 開発体制について

- バグ報告・Pull Request は歓迎します。「大人数で使ったらここが詰まった」という報告は特に助かります。
