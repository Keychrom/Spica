# ⚙️ Spica 環境設定リファレンス (CONFIGURATION.md)

本ドキュメントでは、Spica の動作を制御する環境設定ファイル（`.env`）および管理画面設定の各パラメータについて解説します。

---

## 📁 設定ファイルの位置

Spica は起動時に以下の優先順序で `.env` ファイルを探索し、自動的にロードします：
1. アプリケーションルートディレクトリの `.env`
2. `server/` ディレクトリ直下の `.env`

未指定の項目については、安全な初期値（デフォルト値）が自動的に適用されます。

## 🌐 1. サーバー・ネットワーク設定

| 環境変数名 | 型 | デフォルト値 | 必須 | 説明 |
| :--- | :--- | :--- | :--- | :--- |
| `PORT` | 数値 | `3000` | 任意 | バックエンド Node.js サーバーがリッスンする TCP ポート番号。 |
| `BIND_HOST` | 文字列 | `0.0.0.0` | 任意 | バインドする IP アドレス。`127.0.0.1` を指定するとローカルホストからのみ接続可能になります（Nginx プロキシ配下での推奨）。 |
| `DOMAIN` | 文字列 | `localhost:3000` | **推奨** | 外部公開するサーバーの FQDN（例: `spica.example.com`）。ActivityPub の Actor ID や WebFinger アドレスに使用されます。 |
| `PROTOCOL` | 文字列 | `https` (ローカル時は `http`) | 任意 | 公開プロトコル（`https` または `http`）。インターネット公開時は必ず `https` を使用してください。 |

> [!NOTE]
> `DOMAIN` にプロトコル（`https://`）や末尾スラッシュは含めないでください。自動的に整形されます。

> [!IMPORTANT]
> `DOMAIN` は HTTP Signature の検証でも「署名された host」の候補として使用されます。実際の公開ホスト名と一致していない場合、他サーバーからの配送がすべて署名検証に失敗し、連合が停止します（詳細は「[6. Inbox 署名検証](#-6-inbox-署名検証-http-signature)」）。

## 🔐 6. Inbox 署名検証 (HTTP Signature)

受信した ActivityPub の Activity が「本当にその `actor` 本人から送られたものか」を検証する設定です。  
既定では、検証に失敗した Activity は **401 で拒否** され、なりすまし投稿・改ざん・リプレイ攻撃を防ぎます。

| 環境変数名 | 型 | デフォルト値 | 必須 | 説明 |
| :--- | :--- | :--- | :--- | :--- |
| `INBOX_SIGNATURE_MODE` | 文字列 | `strict` | 任意 | `strict`: 検証失敗を 401 で拒否（**推奨**）。`log`: 警告ログのみで処理を続行（従来挙動・**非推奨**）。 |
| `INBOX_FORWARDED_ACTIVITY_POLICY` | 文字列 | `relay` | 任意 | `relay`: 管理パネルで承認済み（`accepted`）のリレーからの代理転送のみ許可。`any`: 誰からの代理転送でも許可（**非推奨**）。 |
| `SIGNATURE_MAX_AGE_SECONDS` | 数値 | `43200`（12 時間） | 任意 | 署名 `Date` ヘッダーの許容幅（秒）。リプレイ攻撃対策です。 |
| `ALLOW_PRIVATE_REMOTE_FETCH` | 真偽値 | `https` 公開時は `false` | 任意 | プライベート IP・内部ホスト名への remote actor 取得を許可するか（SSRF 対策）。同一 LAN 内の自前ノードと連合テストする場合のみ `true`。 |

### 検証項目

1. `Signature` ヘッダーが存在し、パースできること
2. 署名対象ヘッダーに `(request-target)` が含まれること（署名の別エンドポイントへの転用防止）
3. ボディ付きリクエストでは `digest` が署名対象に含まれ、**実際のボディの SHA-256 と一致**すること（改ざん防止）
4. 署名の `Date` が `SIGNATURE_MAX_AGE_SECONDS` 以内であること（リプレイ防止）
5. 署名鍵（`keyId`）の持ち主が Activity の `actor` と一致し、その鍵で署名が検証できること（なりすまし防止）

### リレーによる代理転送について

公開リレーは、他サーバーの Activity を **自分の鍵で** 転送（inbox forwarding）することがあります。この場合 5 の条件を満たさないため、Spica は **管理パネルで `accepted` 済みのリレー** からの転送に限ってこれを許容します（`INBOX_FORWARDED_ACTIVITY_POLICY=relay`）。承認していない第三者が `actor` を詐称しても拒否されます。

### リバースプロキシ経由時の `DOMAIN` の重要性

Cloudflare Tunnel など Host ヘッダーをローカルオリジンへ書き換える構成では、受信した `Host` が署名時のドメインと一致しません。Spica はこれに対応するため `DOMAIN` の値を署名検証の `host` 候補として試行します。  
したがって **`DOMAIN` が実際の公開ホスト名と一致していないと、すべての受信 Activity が署名検証に失敗します。**

### 連合が停止した場合の切り分け

サーバーログの `[Inbox Rejected]` 行に拒否理由が記録されます。

| ログ中の理由 | 主な原因 |
| :--- | :--- |
| `Signature header missing` / `Malformed Signature header` | 送信側が署名していない、または不正なリクエスト |
| `Digest header does not match the request body` | プロキシによるボディ改変、または改ざん攻撃 |
| `date header is outside the allowed clock skew` | サーバーの時刻ずれ（NTP を確認）、またはリプレイ攻撃 |
| `keyId owner (...) does not match the activity actor (...)` | 未承認のリレー等からの代理転送 |
| `does not verify against the public key` | **`DOMAIN` の設定誤り（最頻出）** |
| `Remote hostname did not resolve` | 相手サーバーの DNS 障害、または SSRF 対策による拒否 |

> [!WARNING]
> `INBOX_SIGNATURE_MODE=log` は署名を検証しないため、**誰でも任意のユーザーになりすまして投稿を注入できます**。原因を特定したら速やかに `strict` へ戻してください。`log` で起動した場合は起動ログに警告が表示されます。

```bash
npx tsx scripts/test-inbox-signature.ts          # 署名強制の検証（15 項目）
npx tsx scripts/test-federation.ts               # 2 ノード間の署名付き連合
npx tsx scripts/test-relay-and-timelines.ts      # 署名付きリレー受信とタイムライン
```

> [!NOTE]

## 🚦 7. レート制限・アップロード上限

| 環境変数名 | 型 | デフォルト値 | 説明 |
| :--- | :--- | :--- | :--- |
| `RATE_LIMIT_DISABLED` | 真偽 | `false` | `true` でレート制限を無効化します（認証 20回/分、API 600回/分、Inbox 3000回/分を IP 単位で制限）。テストや特殊な運用時のみ使用してください。 |

> 画像は 15MB まで（アップロード時に WebP へ変換）です。`MEDIA_MAX_BYTES` は動画・音声に適用されます。

## 🎞️ 8. 動画サムネイル（ffmpeg・任意）

ffmpeg がインストールされていると、動画アップロード時に先頭付近の 1 フレームからサムネイル（WebP）を生成し、タイムラインでは静止画＋再生ボタンで表示します。ffprobe があると再生時間と解像度も記録します。

| 環境変数名 | 型 | デフォルト値 | 説明 |
| :--- | :--- | :--- | :--- |
| `FFMPEG_PATH` | 文字列 | `ffmpeg` | ffmpeg の実行ファイルパス。PATH が通っていない場合はフルパスを指定します（Windows の `.cmd` ラッパーも可）。 |
| `FFPROBE_PATH` | 文字列 | `ffprobe` | ffprobe の実行ファイルパス（任意）。 |

> [!IMPORTANT]
> ffmpeg は**必須ではありません**。未インストールの場合は起動時に検出して機能だけが無効になり、動画のアップロードは従来どおり成功します（サムネイルが付かないだけです）。

## 🗄️ 9. DB メンテナンス（1人運用向け）

リレー経由で流入するリモート投稿は DB を際限なく膨らませます（実測で 1 日あたり数万件）。`npm run db:maintenance` で整理・縮小・バックアップが行えます。詳しい使い方は [SETUP.md](SETUP.md) を参照してください。

| 環境変数名 | 型 | デフォルト値 | 説明 |
| :--- | :--- | :--- | :--- |
| `REMOTE_POST_RETENTION_DAYS` | 数値 | `30` | リモート投稿の保持日数。これより古い投稿を削除対象にします（`0` で期間による削除を行いません）。コマンドの `--days` で上書きできます。 |

| `IMAGE_PROXY_MAX_MB` | 数値 | `512` | 画像プロキシのキャッシュ上限（MB）。超えると最終使用が古いものから削除します。 |
| `IMAGE_PROXY_TTL_DAYS` | 数値 | `30` | 画像プロキシのキャッシュ保持日数。 |

> [!NOTE]
> ブックマーク・ピン留め・ローカル投稿の返信先/引用元・ローカルのリアクション/ブースト・ローカル投稿への返信・フォロー中アクターの投稿は削除対象から除外されます。

> [!TIP]
> `db:maintenance` は ①リモート投稿の整理 ②孤立メディアの削除 ③FTS マージ + VACUUM ④バックアップ ⑤保存方針の適用 ⑥画像プロキシのキャッシュ整理 を行います（`--skip-proxy-cache` で ⑥ を省略できます）。

## 📧 11. メール送信（SMTP・任意）と認証方式

| 環境変数名 | 型 | デフォルト値 | 説明 |
| :--- | :--- | :--- | :--- |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` | 文字列/数値/真偽 | (未設定) / `587` / `false` | SMTP サーバー。通常は管理パネル「メール・認証」から設定します（こちらが優先されます）。 |
| `SMTP_USER` / `SMTP_PASS` | 文字列 | (未設定) | SMTP の認証情報（不要なサーバーでは空欄）。 |
| `SMTP_FROM` | 文字列 | (未設定) | 送信元アドレス。 |

**メール関連の機能は SMTP が設定されているときだけ有効になります**（未設定なら無効）。

- マスターキー復元（確認コード → 新しいキーの送付）
- パスワード方式でのアカウント登録時のメール確認コード（未設定ならコードは要求されません）
- メールアドレスの登録・確認（マスターキー復元用）

認証方式（マスターキー / パスワード）とメール登録の可否は、管理パネル「メール・認証」タブから切り替えます。

### 通報の運営通知

通報が届くと、admin / moderate 権限を持つ運営メンバー全員に `report` 種別の通知が届きます（通知をタップすると管理パネルの通報タブが開きます）。通報者自身には届きません。通知の種類別設定で切ることもできます。

### 権限と監査ログ（複数人で運営する場合）

| 権限 | できること |
| :--- | :--- |
| `admin` | 管理パネルのすべての操作 |
| `moderate` | 通報の対応・ユーザーの凍結/解除・ドメインブロックのみ |

ロールは管理パネルで作成して付与します（最後の管理者を外す操作は拒否されます）。判定に使う権限はこの 2 つで、画面の出し分けは `/api/auth/me` が返す `permissions` で行います。

管理 API への**変更操作は監査ログ**（`admin_actions`）に記録され、管理画面の「監査ログ」タブで「誰が・いつ・何を・どの対象に」を確認できます。パスワードやトークンは記録時に伏せ、拒否された操作（403）は記録しません。保存期間の上限は設けておらず、管理画面から 180 日より古いログを削除できます。

### メール通知（SMTP 設定時のみ）

| 環境変数名 | 型 | デフォルト値 | 説明 |
| :--- | :--- | :--- | :--- |
| `EMAIL_NOTIFICATIONS` | 真偽 | `true` | メール通知機能を有効にするか（SMTP 未設定なら機能ごと無効）。 |
| `EMAIL_BATCH_SECONDS` | 数値 | `60` | たまった通知を 1 通にまとめるまでの待ち時間（秒）。`0` で即時。 |
| `EMAIL_THROTTLE_MINUTES` | 数値 | `5` | 同じユーザーへメールを送る最短間隔（分）。 |

受け取るかどうかは**ユーザーごとのオプトイン**（既定 OFF）で、設定画面の「メールでも通知を受け取る」から切り替えます。宛先は確認済みのメールアドレスのみ。種類別の通知設定で切った種類はメールも飛びません。SMTP 未設定のサーバーでは設定項目ごと表示されません。

## 🖼️ 11-2. 画像プロキシ（リモート画像の直リンク解消）

リモートのアイコンや添付画像をそのまま `<img>` で読むと、**閲覧者の IP と User-Agent が相手サーバーに渡ります**。また相手サーバーが落ちている・画像が消えた・ホットリンクを拒否している場合は表示が壊れます。Spica は既定で、リモート画像をこのノードが取得してキャッシュし、署名付き URL（`/proxy?url=...&s=...`）で配信します（Mastodon の `/proxy` と同じ考え方）。

| 環境変数名 | 型 | デフォルト値 | 説明 |
| :--- | :--- | :--- | :--- |
| `IMAGE_PROXY` | 真偽 | `true` | 画像プロキシを有効にするか。無効にすると相手サーバーから直接読み込みます。 |

- 署名は**インスタンス鍵から導出した HMAC**で、外部からは生成できません（開放プロキシにはなりません）。
- 取得は SSRF ガード・8MB 上限・8秒タイムアウトつきで、**画像以外のコンテンツは配信しません**。
- 配信時は `X-Content-Type-Options: nosniff` と CSP を付け、SVG などを直接開かれてもスクリプトが動かないようにします。
- キャッシュは `server/data/proxy-cache/` に置かれ、毎日の自動整理と `db:maintenance` が期限切れ分・容量超過分を削除します。

> [!NOTE]
> 対象は**画像のみ**です（動画・音声は容量が大きいため直接読み込みのままです）。管理画面のダッシュボード「容量とメンテナンス」から ON/OFF・上限変更・即時整理ができます。

## 🛠️ 管理パネルから変更できる動的設定

以下の項目は、環境変数ではなく **管理パネル（Web UI）** からいつでもリアルタイムに変更・保存できます：

- **サーバールール**: 箇条書きルールの追加・編集・並び替え
- **新規登録時のルール同意必須化**: ON / OFF の切り替え
- **ポリシー URL**: 利用規約、プライバシーポリシー、お問い合わせ先、リポジトリ URL
- **連合リレー**: YUKARI リレー等の ActivityPub 連合リレー追加・削除
- **カスタム絵文字**: サーバー独自絵文字の登録・画像アップロード
- **ドメインブロック / サイレンス**: ドメイン単位の制限。**🚫 ブロック**は通信を 403 で遮断しキャッシュも削除、**🔇 サイレンス**は通信とフォロー関係を維持したまま、そのサーバーの投稿をホーム・ローカル・検索・通知から隠します（データは消さないので後から戻せます）
- **画像プロキシ**: リモート画像をこのノード経由で配信するかの ON/OFF、キャッシュ上限の変更、キャッシュの即時整理（ダッシュボード「容量とメンテナンス」）
- **メール・認証**: SMTP 設定、認証方式（マスターキー / メールアドレス＋パスワード）、登録時のメール確認
- **ストレージ**: S3 / Cloudflare R2 の設定と接続テスト
- **配送キュー**: 配送リトライの滞留・失敗の確認、再送、失敗分のクリア
- **ロール / 権限**: ユーザーごとの権限付与
- **お知らせ**: 全ユーザーへの一斉告知（表示期間つき）

## 🔎 12. 検索索引とリモートコンテンツの保存（DB 肥大化対策）

リレーに参加していると 1 日で数万件のリモート投稿が届き、DB が急速に膨らみます（実測でリモート投稿の索引が DB の約 4 割、フォロー外のブーストが約 1/4 を占めました）。Mastodon / Misskey と同じく、**既定ではリモート投稿の本文を索引せず、フォロー外のブーストも保存しません**。

| 環境変数名 | 型 | デフォルト値 | 説明 |
| :--- | :--- | :--- | :--- |
| `FTS_INDEX_SCOPE` | 文字列 | `local` | 検索索引に入れる範囲。`local`（ローカル投稿のみ・推奨）/ `follows`（＋フォロー中アクターの投稿と自分宛の返信）/ `all`（すべて・旧来の挙動）。 |
| `REMOTE_ANNOUNCE_POLICY` | 文字列 | `follows` | リモートのブースト（リノート）を保存する範囲。`follows`（フォロー中アクターのみ・推奨）/ `all`（すべて）/ `none`（保存しない）。 |

> [!NOTE]
> どちらも **管理画面 → サーバー設定 →「検索とリモート投稿の保存」** から変更できます（DB に保存され、環境変数より優先されます）。

> [!IMPORTANT]
> 設定はこれ以降に届く投稿・ブーストに適用されます。**既に保存済みのデータへ遡って適用**するには、サーバーを停止して `npm run db:maintenance -- --apply` を実行してください（先にバックアップを取ります）。

> [!TIP]
> タイムラインの表示内容は変わりません（変わるのは検索の対象範囲だけです）。ブーストを絞っても、フォロー中の人のブーストと、リレーが配送する投稿本体はそのまま表示されます。

## 🧹 13. 運用の自動化（毎日 1 回の整理とバックアップ）

サーバー常駐のまま、毎日 1 回だけ「バックアップ → 保存・索引の方針の適用 → 保持期間を超えたリモート投稿の削除 → 画像プロキシのキャッシュ整理」を行います。空いた領域を実際に解放する **VACUUM は自動では行いません**（排他ロックが必要なため、サーバーを停止して `npm run db:maintenance -- --apply` を実行します）。

| 環境変数名 | 型 | デフォルト値 | 説明 |
| :--- | :--- | :--- | :--- |
| `AUTO_MAINTENANCE` | 真偽 | `true` | 毎日 1 回の自動整理を行うか。 |
| `AUTO_MAINTENANCE_HOUR` | 数値 | `4` | 実行時刻（0〜23・ローカル時刻）。その時刻以降の最初のチェックで 1 日 1 回だけ実行します。 |
| `AUTO_BACKUP` | 真偽 | `true` | 整理の前に `VACUUM INTO` でバックアップを取るか。 |
| `BACKUPS_KEEP` | 数値 | `3` | バックアップの保持世代数（`server/data/backups/`）。 |

> [!NOTE]
> 管理画面のダッシュボード（「容量とメンテナンス」）から ON/OFF・実行時刻の変更・「いますぐ整理を実行」ができます。バックアップだけを cron で回したい場合は `npm run db:maintenance -- --backup-only` を使ってください。

> [!TIP]
> **外形監視**: `GET /health` が 200 と `{"status":"ok",...}` を返します（DB 異常時は 503）。有効なセッショントークンを付けると、DB サイズ・配送キューの滞留・自動整理の状況も返します。Authorized Fetch 有効時も署名不要で叩けます。

> [!NOTE]
> **グレースフルシャットダウン**: `SIGTERM` / `SIGINT` で新規受付を止め、SSE を閉じ、WAL をチェックポイントしてから終了します（**POSIX 環境のみ**。Windows では強制終了になりますが WAL なのでデータは壊れません）。PM2 / systemd からシグナルが **node プロセスに直接届く**構成にしてください（`npm start` を挟む場合は npm が転送しますが、`node dist/index.js` を直接指定する方が確実です）。
