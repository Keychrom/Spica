## 1. 現状の整理（なぜ作り直すか）

**事実（コードと実画面の実測）**

- React 19 + Vite + Tailwind CSS 3。`client/src` は約 **2.7 万行**。
  `App.tsx` 3,562 行、`AdminDashboard.tsx` 4,527 行、`ModalsView.tsx` 4,829 行、`SettingsView.tsx` 3,942 行。
- 初期 JS は約 347 KB（gzip 109 KB）+ 画面ごとの遅延チャンク。ルーター・状態管理・テスト・lint は未導入。
- URL 契約はすでにある（`/`、`/users/:id`、`/tags/:tag`、`/users/:u/posts/:id`、`/notifications`、`/settings`、`/dm` …）。

**実画面を見て分かった課題（モックアップの根拠）**

1. **画面ごとに骨格が違う。** タイムラインは「左ナビ + 中央 + 右ウィジェット」の3カラムなのに、
   通知・設定・プロフィールでは左ナビが消えて中央1カラムになる。移動のたびにナビの位置が変わり、
   「いまどこにいるか」が常には分からない。
2. **ナビがヘッダーとサイドバーに二重にある。** 通知・管理・テーマ・ユーザーが上下両方にあり、
   どちらを使えばいいか決まっていない。
3. **色の意味が混在。** 投稿ボタンは緑、アクセントは紫、タグはシアン、タイムラインタブはエメラルド、
   Live も緑。しかもアクセント色は Tailwind のクラスを `!important` で上書きして実現している
   （`index.css` の `[data-accent]` ブロック）ため、色を足すほど CSS が壊れやすくなる。
4. **情報密度がバラバラ。** `text-[10px]`・`text-xs` が混在し、余白も場当たり。同じ画面で字の大きさが 5 段階ある。
5. **モバイルとデスクトップで別物。** モバイルは上部タブ + 下部バー + FAB が全部入りで、要素が重複して見える。

**つまり:** 「見た目を変えたい」以前に、**画面の骨格・色の意味・密度の基準がない**ことが作り直しの理由です。

## 2. 再構築の前提（提案）

**維持する**
- サーバー API の形（`server/` は触らない。クライアントの都合で API を変えない）
- URL 契約（OGP 差し込みがサーバー側にあるため。SPA のパスは増やせるが既存は壊さない）
- PWA（Service Worker・Web Push・ホーム画面追加）、テーマ切替・アクセント色の**機能**
- Fediverse の作法（CW・公開範囲・リアクション・カスタム絵文字・ALT・引用・アンケート）

**変える**
- 画面骨格の統一（全画面で同じシェル）とレスポンシブの作り直し
- デザイントークン（CSS 変数 → Tailwind v4 の `@theme`）でダーク/ライト/OLED/アクセントを正規化
  （`!important` 上書きの廃止）
- ルーター導入（`react-router`）+ 画面単位のコード分割はそのまま
- 状態の置き場所を画面ごとに閉じる（`App.tsx` の巨大 state を解体）
- lint / テスト（Vitest: api と純関数のみ）の導入

**技術方針（たたき台・決定は次段階）**

| 項目 | 提案 | 理由 |
| :--- | :--- | :--- |
| フレームワーク | React 19 + Vite + TS（維持） | サーバーは `client/dist` を配信するだけ。移行が最も安い |
| スタイル | Tailwind CSS **4**（CSS-first トークン） | CSS 変数ベースのテーマを正規の方法で扱える |
| ルーター | **react-router v7** | URL 契約が既にある。自前 pushState 18 か所を廃止 |
| サーバー状態 | 薄い自前フック + AbortController（必要なら TanStack Query） | 依存を増やしすぎない |
| タイムライン | **react-virtuoso 継続** | 1000 行でも DOM ノード一定の実績がある |
| アイコン | lucide-react 継続 | 現行と同じ |
| テスト | Vitest + ESLint | 現状ゼロ。api/ と純関数だけでも回帰を防げる |

**着手前にやること（重要）**
- このフォルダは **git 管理下にありません**（`.git` がない）。作り直す前に
  `git init` + 初回コミット、または `client/` のバックアップを強く推奨します。
- 並行して**旧 UI を残す**場合に備え、切り替え単位（画面 or 一括）を先に決めます。

## 3. 前半3案（いまの延長で質を上げる）

前半の3案は「いまの延長で質を上げる」方向です。骨格（左ナビ＋中央＋右ウィジェット）はほぼ現在のまま、
色・余白・密度・区切り方を整えます。

| 観点 | **A STELLAR** | **B DAYLIGHT** | **C DECK** |
| :--- | :--- | :--- | :--- |
| トーン | 静かな星夜 | 真珠の白・紙 | 管制塔・道具 |
| 既定テーマ | ダーク | ライト | ダーク |
| アクセント | スピカ紫 `#8B8DFF` | バイオレット `#6D5AE6` + 真珠 | 星光アンバー `#FFA53B` |
| レイアウト | 3カラム・中央640固定 | 3カラム・中央640固定 | レール + カラム並列（430×N） |
| 情報密度 | 中 | 低（ゆったり） | 高 |
| 区切り方 | ヘアライン | 柔らかい影 | 罫線 + 等幅 |
| 主な対象 | 現行ユーザー・夜に使う人 | 新規・ライトユーザー | ヘビーユーザー・PC常用 |
| 移行のしやすさ | ◎ 現行の延長 | ○ 色は別物 | △ IA が変わる |
| 実装コスト | 中 | 中 | 大（キーボードUI含む） |

### A. STELLAR（推奨の主軸・据わり重視）
名前の由来「スピカ（真珠星）」にいちばん近い、**夜空のダーク**。現行の雰囲気を残すので既存ユーザーの違和感が最小。
- ヘアライン（罫線）で区切り、カードの箱を減らす → スクロールが軽く見える
- アクセント 1 色（紫）。緑＝接続中、赤＝削除だけに固定
- 長文の行間を 1.85 に広げ、本文 15px（現行より読みやすく）

### B. DAYLIGHT（ライトテーマとして同梱を推奨）
白い紙 + 柔らかい影。**昼間・スマホ・新規ユーザー**にいちばん優しい。
- 影で区切るので境界線が減り、明るく軽い
- 余白 1.2 倍・本文 15.5px
- ロゴの真珠グラデーション（ラベンダー→ピンク）だけが Spica の色

### C. DECK（密度オプションとして段階導入を推奨）
ホーム/ローカル/通知を**横に並べて同時に追える**。`j/k` 移動、`r` 返信、`n` 投稿。
- 1 行 64px・本文 13.5px・ハンドルは等幅 → 同じ画面に 2 倍の投稿
- 下部にキーボードヒント、SSE 接続状態を常時表示
- IA（情報の並べ方）自体が変わるので、これだけは「別アプリ」に近い作り

## 3b. 後半3案（既存の見た目を大きく壊す）

後半の3案は、**見た目の言語そのものを変える**方向です。装飾（立体・ガラス・ネオン・強いグラデーション）は
いっさい使わず、**組版・意匠・造形**という、人が長く積み上げてきた型で作ります。
「AI が量産した画面」に見える原因はたいてい装飾なので、そこを全部捨てるのが出発点です。

| 観点 | **D 活字** | **E 墨** | **F 構成** |
| :--- | :--- | :--- | :--- |
| モチーフ | 新聞・活版印刷 | 和紙・墨・朱印 | 構成主義・モダニズム |
| 本文の書体 | 明朝 | 明朝 | ゴシック（見出しは極太） |
| アクセント | 朱 `#B4341F` 1色 + 藍（リンク） | 朱 `#A8342A` 1色 + 藍 | 赤・黄・青（**意味に固定**） |
| 骨格 | 題字（マストヘッド）＋段組＋欄外 | 背表紙（縦書きナビ）＋本文＋余白 | 面番号の帯＋3帯 |
| リアクション | 朱の円印 | 朱の円印 | 円 + 数字 |
| 操作の見せ方 | 小さな文字（返信・リノート…） | 小さな文字と中黒 | 大文字ラベル + 番号 |
| 反転（ダーク） | 夜刊として成立 | 夜の墨として成立 | 反転可 |
| 破壊度 | 大 | 大 | 大 |
| 実装コスト | 中 | 中 | 中 |
| 向いている | 読む・引用・議論 | 和の identity | 遠目で分かる・紹介 |

### D. 活字（KATSUJI）— 紙面
タイムラインを**紙面**として組む。角丸・影・グラデーションを全部やめ、明朝体の本文・ゴシックのラベル・
罫線（1px と 3px 二重）だけで作ります。時刻は記事の左肩、画像の説明（ALT）は**キャプション**、
リアクションは**朱の印**。題字の下の「段」がナビになり、右は欄外（タグの目次・奥付・登場人物）。
**破壊度が高いのに読みやすさを落としていない**のが強みで、長文・引用・議論の多い Fediverse と相性が良い。

### E. 墨（SUMI）— 和紙と墨と朱印
和紙の地に墨の文字、差し色は**朱ただ一点**。左のナビは**縦書きの背表紙**（本の背のように面が並ぶ）、
アバターは**印**の枠、リアクションは**朱印**、投稿は**原稿用紙の方眼**にしたためる。
最も強い identity が出る案。和の意匠は好き嫌いが分かれるため、**テーマとして選べる**形が現実的。

### F. 構成（KŌSEI）— 幾何と原色のポスター
極太のゴシック、太い黒罫、原色（赤・黄・青）。面（画面）と投稿に**通し番号**を振り、
左の帯に大きな面番号と縦書きの見出し。色は意味に固定（赤＝操作、黄＝印、青＝参照）。
本文は無装飾の黒文字にして読書性を守り、**強い造形は画面の骨にだけ**使う。
遠目でも「Spica の画面」と分かるのが価値。

**3案に共通する思想**: 装飾で個性を出さない。組版・余白・罫・色の意味で出す。
そのほうが古びず、生成り（AI っぽさ）にも見えない。

## 3c. 追加2案（シンプルさ・ミニマリズム・エレガンス）

「装飾で個性を出す」の反対側です。**引き算と精度**で作る2案で、どちらも
**設計規則（トークン・部品・検査）を画面として同梱**しています。これが「コードの正しさに焦点を当てたデザイン」の具体化です。

| 観点 | **G 素（PLAIN）** | **H 雅（MIYABI）** |
| :--- | :--- | :--- |
| 作る方法 | 引き算（引くほど良くなる） | 精度（余白・字面・陰影を揃える） |
| テーマ | ライト + ダーク（同一トークン） | ライト（暖色の象牙） |
| 色 | 6 個 + 注意色 1（#FFFFFF / #FAFAFA / #EAEAEA / #111315 / #6B7078 / #2563EB） | 象牙 #FBFAF7 / 墨 #1C1A17 / 罫 #E8E3D9 / 青緑 #12564F（+ 金は題字の印だけ） |
| 書体 | ゴシック 1 系統・6 段 | ゴシック + セリフ（題字と見出しだけ）・5 段 |
| 形 | 角丸 1 種（6px）・**影 0** | 角丸 2 種（10px / ピル）・影 2 トークン |
| 骨格 | 2 カラム（右のウィジェット列は**既定で無し**） | 3 カラム（余白広め・淡い罫） |
| リアクション | 文字と数字（枠なし。押したものだけ色） | 細い縁のピル（等幅数字） |
| 実装コスト | **小**（部品 8 個・規則が機械検査できる） | 小〜中 |
| 向いている | 道具として長く使う・変更に強い土台 | 長く使っても疲れない・「静かに上質」 |

### G. 素（PLAIN）— 引き算のミニマリズム
色 6 個・角丸 1 種・影 0・字 6 段・余白は 4px の倍数だけ。**右のウィジェット列を既定で消し**
（タグやサーバー情報は専用ページへ）、タイムラインは 1px の罫だけで区切ります。
美しさは装飾ではなく整列と余白の一貫性から出します。

**「03 システム」がこの案の本体**です。トークン → 部品 8 個 → 構造 → 検査できる規則、の 4 段で、
設計を**コードとして検査できる形**で書いています:

- トークン定義以外に色を書かない（`#hex`・`rgb()` の出現 0 件）— grep
- `!important` を使わない — grep
- 余白・寸法は `--s-*` 以外を使わない（4px の倍数）— レビュー
- 角丸は 1 種類、影は使わない
- アイコンのサイズは 16 / 20 の 2 種類だけ
- 遷移は 120ms / 180ms の 2 種類だけ
- 部品は `components/` の 8 個にだけ置く（画面側にスタイルを書かない）

つまり「デザインが崩れない」を人の注意力ではなく**機械**で守る作りです。

### H. 雅（MIYABI）— エレガンス
象牙の地に墨の字、アクセントは深い青緑 1 色。**派手さではなく精度**で上質を作ります。
- セリフは題字・画面名・数字だけ（本文まで明朝にすると重くなる）
- 数字（時刻・件数・票数）は**常に等幅**（tabular）→ 桁が揃い、一覧の精度が上がる
- 本文の行長は **62 字まで**（読み疲れの主因は行長）
- 影は 2 トークン、角丸は 2 種類、ボタンは丸（pill）だけ
- 金（#A98A4B）は題字の小さな印にだけ使う

「静かだけど安く見えない」を、規則の少なさと規律の高さで作る方向です。

## 3d. 組み合わせ案（I 白雅 / J 紫雅 — B × H）

「案H の雅が好き。色合いと骨格ベースは案B」というご要望から、**掛け合わせを 2 方向**つくりました。
同じ 2 案の混ぜ方でも、どちらを土台にするかで印象が変わります。

- **I 白雅（HAKUGA）** = 案B の骨格 ＋ 案B の色 ＋ 案H の規律 → 案B の使い心地を保って、字面と質感を上げる
- **J 紫雅（MURASAKI）** = 案H の骨格 ＋ 案H の部品 ＋ 案B の色 → 案H の佇まいを保って、色みをクールに寄せる
- **K 雅＋（MIYABI PLUS）** = 案H そのもの ＋ 案B の色 ＋ 案B のデスクトップ上部（セグメントタブ・新着ピル・リロード）→ 案H の良さを薄めずに、色と上部だけを差し替える

### I の中身

| 要素 | 由来 | 中身 |
| :--- | :--- | :--- |
| 色 | **案B** | 薄ラベンダーの地 #F4F5FA / 白い面 / スミレ #6D5AE6 / 真珠のグラデーション（ロゴと自分のアバターだけ） |
| 骨格 | **案B** | 左ナビ 264 / 中央 640 / 右 330、カード型フィード、セグメント式タブ、右にカード 3 枚 |
| 字面 | **案H** | セリフは題字と画面名だけ、本文はゴシック 15px / 行間 1.9 / 行長 62 字、ラベルは字間 .16em |
| 数字 | **案H** | 時刻・件数・票数は必ず等幅（tabular-nums） |
| 形と影 | **案H** | 角丸は 10 とピル（999）の 2 種だけ、影は 2 トークン（置いてある面／浮く面） |
| 部品 | **案H** | 細い縁のリアクションピル、円のアバター（淡い輪）、文字のアクション |
| ダーク | **案B の系統** | 同じトークンを暗く反転（モックの 04 に実例） |

**「システム」表に由来を明記**しています。どの値がどの案から来たかが分かるので、
あとで「やっぱり色だけ案H に寄せる」「骨格を案G の2カラムにする」といった変更がトークンの差し替えで済みます。

### J の中身

| 要素 | 由来 | 中身 |
| :--- | :--- | :--- |
| 骨格 | **案H** | 236 / 640 / 300、余白広め、**カードを使わずヘアラインで区切る**（I は案B のカード型フィード） |
| 部品 | **案H** | 下線のタブ（I は案B のセグメント）、細い縁のリアクションピル、円のアバター |
| 字面 | **案H** | セリフは題字と画面名だけ、本文 15px / 1.9 / 62 字、数字は等幅 |
| 色 | **案B / 案I** | 薄ラベンダーの地・白・スミレ・真珠のグラデーション（ロゴと自分のアバターだけ） |
| モバイル | 共通 | 上部のアバター → ドロワーで全項目（下の「モバイルのナビゲーション」参照） |

### K の中身（案H そのもの ＋ 案B の色とデスクトップ上部）

**土台は案H です**（案J から派生したものではありません）。案H の骨格・余白・部品・字面・モバイル（左上のアバター→ドロワー）はすべてそのまま残し、
違うのは次の 2 つだけです。

| 変えたもの | 案H | 案K |
| :--- | :--- | :--- |
| 色 | 象牙 #FBFAF7 / 墨 #1C1A17 / 青緑 #12564F | **案B / 案I のパレット**（地 #F4F5FA・面 #FFFFFF・罫 #E8EAF3・字 #191C26・操作 #6D5AE6・真珠はロゴだけ） |
| デスクトップ上部 | 下線タブ + 件数の文字だけ | **案B の3要素** — セグメントタブ（ホーム/ローカル/連合）・新着ピル・リロードボタン |

**採用後の変更（2026-10-09）**

| 変更 | 内容 |
| :--- | :--- |
| **明朝体をやめた** | K の採用後、「明朝体はやめて」という判断で **書体は 1 系統（すべてゴシック）** になりました。見出しは太さ（700）と字間で階層を作ります。追加の書体は読み込みません（実装: `--serif` トークンは削除済み） |
| **画面名がタブに追従** | 「ホーム」で固定だった画面名を、選んでいるタブ（ホーム / ローカル / 連合）に合わせるようにしました。タグページ（`/tags/:tag`）では `#タグ` になります |
| **左右の列に 1 本線** | 左ナビの右端と欄外の左端に縦線を入れました（色は投稿間の罫と同じ `--line-soft`）。列の境目が分かり、視線が迷いません |
| **ウィジェットを平らに** | 欄外のカードから枠と影を外し、罫線の区切りだけにしました（立体感をなくす）。浮かせる面はモーダルとリアクションの選択だけです |

戻した3要素は**サイドバーと同じ言語**で描いています（これが大事なところ）:

| 部品 | 見た目 | そろえた先 |
| :--- | :--- | :--- |
| タブ（ホーム/ローカル/連合） | 文字だけ。選択中は角丸 10 の淡い塗り（`--surface`）、影なし | **サイドバーの項目と同じ形・同じ塗り** |
| 新着 | 淡いアクセントの面（`--accent-soft`）+ スミレの文字 | 公開範囲バッジと同じ言語 |
| リロード | 素のアイコン（枠も影も持たない） | サイドバーの静かなアイコン |

つまり「上部だけ別のシステム」にならないように、**ソリッドなアクセント塗りは「ノートを作成 / 投稿」だけに残し**、
それ以外の面はすべて淡い塗りに統一しました（見た目だけの変更で、機能は同じ）。
新しい色は 1 つも足していないので、「色は 9 トークンだけ」という検査規則がそのまま通ります。
モバイルは案H のまま（下線タブ + 左上のアバター→ドロワー）。デスクトップと同じタブに揃えることもできます。

**I と J と K の選び方**: 「案B のカード型で親しみやすく、字面だけ上質に」なら I。「案H の静けさと余白が好きで、色だけ明るくしたい」なら J。「J の静けさはいいが、タブと新着が物足りない」なら K。

## 4. 推奨

**据わり（使い勝手と移行の確実さ）を取るなら A。身元（Spica と一目で分かる見た目）を取るなら D 活字。土台の正しさを最優先するなら G 素。**

**今回のご要望（案B の色と骨格 × 案H の雅）は 2 方向つくってあります — 案I（案B の骨格＋案H の規律）と案J（案H の骨格＋案B の色）。**
どちらも読みやすく、実装は小さく、テーマの差し替えで互いに行き来できます。カード型で親しみやすさを残すなら I、余白と静けさを優先するなら J が候補です。

**もう一つの組み合わせ方は「骨格とトークンは G、見た目は選んだ案」。**
G の「03 システム」（トークン・部品 8 個・検査規則）は**どの案にも流用できる土台**です。
たとえば「トークンと部品は G のまま、本文と見出しの組版を D（活字）にする」「H の字面規則（等幅数字・行長 62 字）を
全案の共通規則にする」といった重ね方ができます。H は G と同じ骨格のまま上質側に振った案なので、**テーマとして同居**できます。

- **A + B を同梱**: テーマは「トークンの切替」なので、A を正しく作れば **B のライトはほぼ無料**で付いてくる
  （現行もライト/OLED があるが `!important` 上書きなので、作り直しで初めて正しく実装できる）。
  C の良さ（コンパクト表示・キーボード操作）は、あとから表示オプションとして足せる。
- **D 活字が本命になり得る理由**: 破壊度が高いのに、読みやすさを落としていない。
  明朝体の長文は疲れにくく、罫線だけで組む画面は情報量が多く見える。Fediverse のクライアントは
  Misskey / Mastodon の類似品が多いので、**「新聞」という見た目は記憶に残る**。
- **E 墨 / F 構成の扱い**: どちらも強いが好き嫌いが分かれる。**主画面に固定せず、テーマ（トークン）として選べる**
  形にするのが現実的（同じ骨格で作れるので、実装は増えない）。特に E は和の意匠の好みが分かれるため、
  「既定は D、設定で E/F/A/B に切替」のような扱いが安全。

**どの組み合わせでも共通**: 全画面で骨格を統一し、テーマは CSS 変数の差し替えで実装する
（`!important` の上書きを廃止することが、テーマを増やしても壊れない前提）。

## 4b. D/E/F を実装するときの注意（現実性）

モックは「見た目」なので、実装時に判断が要る点を先に書いておきます。

| 論点 | 現実的な解 |
| :--- | :--- |
| **明朝体（D/E）** | Web フォント（Noto Serif JP）は数 MB あり重い。**システムの明朝**（Windows: Yu Mincho / macOS: Hiragino Mincho / Android: Noto Serif JP）を第一候補にし、必要な人だけ設定で Web フォントを読み込む。デバイスで字形が変わることは受け入れる |
| **縦書きナビ（E）** | 画面の高さに依存する（項目が多いと入らない）。**主要 5 項目だけ縦書き**にし、残りは横書きの引き出しに。ホバーで横書きラベルを出す併用も可 |
| **原稿用紙の方眼（D/E）** | CSS の `repeating-linear-gradient` だけで実装できる（画像不要・数 KB）。入力欄だけに使う |
| **紙の質感（D/E）** | SVG の `feTurbulence` を data URI で 1 枚。**固定オーバーレイは描画コストがかかる**ので、背景色に薄く敷く形にする |
| **反転テーマ（夜刊／夜の墨）** | トークンの差し替えだけで動く（モックで実証済み）。実装は変数を増やすだけ |
| **アイコンをやめる（D/E）** | 操作を文字（返信・リノート…）にすると、アイコンより分かりやすく、実装も軽い。ただし**横幅を食う**のでモバイルはアイコン + ラベルに |
| **視認性** | 明朝体は小さいと潰れる。**本文 15px 以上**を守る。朱は濃いめ（`#A8342A` 前後）にして 4.5:1 を確保 |
| **原色（F）** | 黄は**背景に敷かない**（文字のコントラストが落ちる）。印・帯・塗りに限定する |

## 5. どの案でも共通にする情報設計

**骨格（デスクトップ ≥1280px）**
```
┌── 左ナビ（全画面で常設）──┬──── メイン 640–720px ────┬── 右（文脈）──┐
│ ロゴ / ナビ / 投稿ボタン   │ 画面ごとの中身              │ 検索・タグ      │
│ ユーザーカード（最下部）   │ （通知・設定・プロフィールも）│ サーバー情報    │
└──────────────────────────┴───────────────────────────┴───────────────┘
```
- **通知・設定・プロフィール・ブックマークでも左ナビを消さない**（現状の最大の欠点を修正）
- ヘッダーの重複を解消: 検索は右カラム、通知/テーマ/ユーザーはナビに一本化

**モバイル（<768px）— 左ナビは「ドロワー」になる**

デスクトップの左ナビと同じ並びを、左上のアバターから開く引き出しとして持たせます。
「サイドバーが見えないと設定に行けない」を防ぐための決めごとです。

```
┌──────────────────────────────┐   アバターをタップ
│ (す)   画面名          新着 2 │   ┌────────────────┬────────────┐
│ ホーム  ローカル  連合         │   │ Spica          │            │
│                              │   │ すいれん @suiren│ （画面は    │
│   投稿のリスト…        (投稿) │ → │ ホーム          │  薄暗く）   │
│                              │   │ 通知 3          │            │
├──────────────────────────────┤   │ 見つける        │            │
│ ホーム   検索   通知(3)  自分  │   │ メッセージ / ブックマーク       │
└──────────────────────────────┘   │ ── まとめ ──    │            │
                                   │ リスト / アンテナ / チャンネル / ドライブ
                                   │ 設定 / 管理パネル │            │
                                   │ ライト・ダーク・端末 ／ ログアウト│
                                   └────────────────┴────────────┘
```

- **デスクトップの左ナビ ＝ モバイルのドロワー**（同じ並び・同じ順）。画面ごとにナビが消えない原則をモバイルでも守る
- 下部バーは「よく行く 4 つ」だけ（ホーム・検索・通知・自分）。残りは必ずドロワーから届く
- 投稿は右下の FAB（ドロワーを開かずに書ける）
- 上部は「アバター（メニュー）/ 画面名 / 新着」、その下にタイムラインのタブ（下線）
- 検査規則: **主要動線は 4 + 投稿。すべての画面へ 2 タップ以内**（下部バー or ドロワー）

**投稿カードの解剖（3案共通）**
```
[アバター] 名前 @handle ・時刻            [公開範囲バッジ]
           本文（行間広め・タグは色リンク）
           CW（折りたたみ）  → 添付（1–4枚 + ALTバッジ）
           引用カード / アンケート
           [★ 4] [✦ 2] [+]          ← リアクション
           返信 ・ リノート ・ 引用 ・ 共有 ・ ブックマーク
```

**用語は現行を維持**（ノート / リアクション / リノート / 連合・ローカル・フォロワー / アンテナ / チャンネル / ドライブ）。

## 8. モックアップの読み方と注意

- 静的 HTML + 素の CSS（Tailwind 不使用）。**表現用の装飾は実装時にトークンへ落とします**。
  A/B/C には柔らかい影やグラデーションが入っていますが、これは「面の関係」を示すためのもので、
  実装では影の値をトークン（1つか2つ）に固定します。D/E/F は影・角丸・グラデーションを**使っていません**。
- 画像はダミーです（A/B/C はグラデーション、D/E/F は罫のハッチ、G/H はハッチ＋面の色）。
- G/H の「システム」節は、そのまま実装の仕様（トークン名・部品・検査規則）として使えます。
- 明朝体は**システムフォント**で描いています（Yu Mincho など）。配布物にフォントを含めるかは実装時に決めます。
- モックの文字・ユーザー（すいれん / みかん / @mikan@misskey.io など）は**すべてサンプル**です。
- 各ファイルは独立して開けます。`index.html` からリンクしています。
- 方向が決まったら、この `design/` フォルダは `docs/` の設計文書に置き換えて削除する想定です。
